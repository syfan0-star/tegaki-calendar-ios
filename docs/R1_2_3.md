### 1.1 使う人に見える変化

- **普段（同じアカウントのまま）**: 何も変わりません。裏から戻ったときの同期の始まりが、確かめの 2 つの呼び出しの分（ふつうは 1 秒もかからない）遅れるだけです。確かめが終わるまでは、開いたページを 1 枚だけ取りに行く処理を省きます（すぐ後の取得が同じ物を持ってきます）。
- **アプリを閉じている間や裏にいる間に、別の Apple アカウントにした場合**: 今は、一時的な失敗や順番しだいで、黙って新しいアカウントへ全部のページを送ったり、新しいアカウントの手書きを取り込んだりすることがありました。これからは、最初の往復で「停止中」になり、「別の iCloud アカウントです」の問い合わせが出ます（DESIGN §5.4 のとおり）。
- **アカウントが確かめられていないときに「この端末の手書きを全て消す」を押した場合**: 端末の中は今までどおりすぐ消えます。iCloud の分は確かめの後に回し、確かめられなければ今ある「iCloud の手書きを消せませんでした。この端末の分は消しました…」のお知らせを出します（文言は変えません）。同じアカウントと確かめた次の同期で iCloud の分も消えます。別のアカウントと分かって「手書きを残して使い始める」を選んだら、保留の削除はしません（§11 の 3）。
- **同期の途中でアカウントが変わった場合**: 送信中の 1 ページを除き、残りは送りません。すぐ次の同期が確かめて表示を決めます。

### 1.2 CloudKit への呼び出しが増える所（費用）

増えるのは `accountStatus()`（端末の中の問い合わせで、ふつうは通信しない）と `userRecordName()`（2 回目からはたいてい CloudKit が覚えている【未確認。実機では計っていない／Apple の資料で確かめていない】）の組だけです。取得・送信・削除の数は変わりません（別のアカウントのときは、全ページを送り直さないので大きく減ります）。

- 裏から前面に戻るたびに 1 組。`.inactive` だけ（コントロールセンター・アプリの切り替え画面・Apple のシート）では増えません。
- 裏にいるあいだの往復ごとに 1 組。たいていは、裏に回るときの保存による 1.5 秒後の送信の 1 回だけ。ほかに、裏での再試行とサイレントプッシュ。
- サイレントプッシュごとに 1 組。**前面で 2 台が同時に書いているあいだは、相手の送信ごとにプッシュが来るので、そのたびに 1 組増えます**（裏では iOS がプッシュを 1 時間に数回に絞ります【未確認。実機では計っていない／Apple の資料で確かめていない】）。
- 前面で起動したときに、もう 1 組になることがあります（起動の往復の確かめと、最初の前面の確かめ）。
- 確かめに失敗した後（オフラインなど）は、次の往復も確かめから始まります。

### 1.3 裏で使える時間

- このアプリは `beginBackgroundTask`（裏で少し長く動くための iOS の仕組み）を使っていません。裏に回った後に動けるのは**数秒**です【未確認。実機では計っていない／Apple の資料で確かめていない】（サイレントプッシュのときの約 30 秒とは別）。裏に回るときの送信は、送る前に確かめの 2 つを待つので、途中で止められやすくなります。止められても、ページは「送っていない」印のまま残り、次の前面で送ります（データは失いません）。止められた往復が後で起きたときの扱いは §3.5。
- サイレントプッシュの 20 秒の予算は変わりません。確かめはその 1 周の中に入り、20 秒を過ぎれば今までどおり「新しいデータ無し」を返して 1 周は続けます。

## 2. 穴（何が起きうるか）

診断（読むだけの調べ、2026-11-09）と、計画への 2 人の批評で見つかった穴です。行の番号は 1.2.2 の `Sync/SyncEngine.swift`。

- **G1（確かめの失敗が「確かめ済み」に化ける）**: `checkAccount()` は await の前に `accountCheckRequested = false` にし、`accountStatus()` の throw・`.temporarilyUnavailable`・`userRecordName()` の throw のどれでも、戻さずに false を返していました（:461-492）。前にアカウントを記録した端末で、status が `.offline`・`.pending`・`.error` だと、`needsAccountCheck` はその起動のあいだずっと false になり、再試行と前面の `syncNow` が確かめずに往復します。アプリを閉じている間に Apple アカウントを切り替えていると、次の成功した往復は**新しいアカウント**と話します。新しいアカウントにはゾーンが無いので `zoneMissing` → `recoverFromZoneLoss` が端末の全ページを送るべき物にして、新しいアカウントへ全部送ります（または新しいアカウントのページを端末のファイルに混ぜます）。起動の確かめ（`start()` の注釈、M4_CONTRACT §4.5 の 8）はまさにこのためにありました。
- **G2（cycle の外の仕事に関門が無い）**: `run(.pushOnly)`・`fetchPage`・取り込みの `saveMeta`（:334）・全消去は `accountConfirmed` だけを見ていて、`accountCheckRequested` を見ません。アカウントの変更の前に積んだ 1.5 秒後の送信・`pushAgain`・取り込みの送信は、変更の後に走っても送っていました。
- **G3（裏からの戻りの順番）**: アプリが停止している間に過ぎたタイマー（再試行・1.5 秒後の送信）と、裏で受けたサイレントプッシュは、`.CKAccountChanged` が届いて処理されるより先に往復を始めることがあります。確定済みのアカウントには確かめをしません。iPhone・iPad で Apple アカウントを切り替えるのはふつう「設定」アプリの中、つまりこのアプリが裏にいるか停止している間です。
- **走っている仕事が止まらない**（診断の確かめで見つけた）: `.CKAccountChanged` は `workEpoch` を進めていませんでした（:514-517。:92 の注釈とも合わない）。送信中の push のループは残りのページを新しいアカウントへ送り続け、取得中の pull は新しいアカウントの記録を混ぜていました。
- **M1（epoch の取り直し）**（批評 1・2）: pull・push・`cloudErase` は epoch を自分の頭で取り直していました（:564・:690・:787）。そのため、確かめ（`checkAccount`）の await や `ensureZone` の await の間に来た `.CKAccountChanged` を見逃します。保留の全消去なら、別のアカウントの記録を消しえました（:379-381 は最初の `checkEpoch` より前）。
- **M2（停止をまたぐ往復）**（批評 1）: 裏に回るときの送信は、送っている途中で iOS に止められるのが普通です。その間にアカウントを切り替えると、起きたときに止まっていた往復が続きのページを新しいアカウントへ送ります。
- **M3（ゾーン消失が「全部送る」に化ける）**（批評 1）: 切り替えた直後のアカウントではたいてい `zoneMissing` が返ります。`run` と `fetchPage` はこれを受けると確かめずに `recoverFromZoneLoss` で全部を送り直していました。
- **前からある穴（全消去と「手書きを残す」）**: `adoptAccount` は `pendingCloudErase` を保つので、前のアカウントで保留になっていた iCloud の全消去が、新しいアカウントの手書きを全部消しえました（M4.md §4.1 の「別アカウントのレコードを後で消さないため」に反する）。

## 3. エンジンの変更（`Sync/SyncEngine.swift`、ほかに 2 ファイル）

### 3.1 G1: 確かめの頼みを残す

`checkAccount()` は await の前に `accountCheckRequested = false` にするのは今のまま（確かめの途中に来た `.CKAccountChanged` がもう一度頼めるように）。アカウントを確定も拒否もしなかった 3 つの戻り方（`accountStatus()` の throw、`.temporarilyUnavailable`、`userRecordName()` の throw）で `true` に戻します。`noAccount` などの `localOnly` と別アカウント（`pendingAccount`）は、status か `pendingAccount` で `needsAccountCheck` がもともと true なので変えません。確定したときは、問い合わせた時刻（`checkAccount()` の頭で取る `askedAt`）を `accountCheckedAt` に記録します（§3.5）。

### 3.2 G2: cycle の外の仕事の関門

```swift
private func confirmedForSending() async -> Bool {
    guard accountConfirmed else { return false }   // 一度も確定していないアカウントは cycle だけが確定する
    guard needsAccountCheck else { return true }
    let epoch = workEpoch
    guard await checkAccount() else { return false }
    return epoch == workEpoch                       // 確かめの途中に .CKAccountChanged が来たら使わない
}
```

- `run(.pushOnly)` は `guard accountConfirmed` を `guard await confirmedForSending()` にする。
- 取り込みの `Meta` の保存も、走る時点でこの関門を通す。`saveMeta` は epoch を受け取り、保存のたびに確かめる（変わっていれば覚えずにやめる）。
- 全消去の iCloud の分（`eraseEverything` の待ち行列の中身）も関門を通す。通らなければ `CloudError.other("account")` を返して throw（status は確かめが決めたまま。`handleFailure` は呼ばない）。`Interrupted` で止まったときも同じ。
- `pageOpened` と `fetchPage` は `guard accountConfirmed` を `guard !needsAccountCheck` にする（確かめが待っているあいだは 1 ページの取得を省く。`pageOpened` では 30 秒の冷却を記録する前に省くので、確かめの後に開いたページはまた取りに行ける。`fetchPage` は積んだ時と走る時の両方で見る）。

### 3.3 G3: 裏にいる印

- 新しい `private var awayFromForeground`。`applicationDidEnterBackground()`（新しい公開の口）で true、`applicationDidBecomeActive()` で false。アプリのエンジン（`live()`）は true で始まる（裏での起動のため。テストのエンジンと `screenshotDemo` は false）。
- `needsAccountCheck` に `awayFromForeground` を入れる。裏にいるあいだは、どの往復（再試行・1.5 秒後の送信・サイレントプッシュ・取り込み・全消去）も確かめから始める。**裏でした確かめが成功しても印は残す**（その後の停止中に切り替えられることがあるため）。
- `applicationDidBecomeActive()`: 印があれば下ろし、確かめを頼み、`workEpoch` を進める（iOS が止めていた往復を止める）。素の `Task` だった `syncNow` は `spawn`（数えられる仕事）にする。本番の動きは同じで、テストの `waitUntilIdle` が待てるようになる。
- `handleRemoteNotification`: 自分の購読の知らせなら確かめを頼み、裏にいるなら `workEpoch` も進める。
- `CalendarRootScreen`: `scenePhaseChanged()` の `.background` の枝で `sync.applicationDidEnterBackground()`（`.inactive` では呼ばない。iPhone と全画面の iPad では、アカウントの切り替えに「設定」アプリを開くので `.background` を通る。Split View・Slide Over・Mac で通らない場合は §11.2。そのときは `.CKAccountChanged` の epoch で止まる）。`appear()` で `scenePhase == .active` なら `sync.applicationDidBecomeActive()`（`.onChange(of: scenePhase)` は最初の値を知らせないので、初めから `.active` で現れた起動では印が下りないままになるため。M4_CONTRACT §5.3 の表にもともと書いてあった呼び出し）。

### 3.4 走っている仕事を止める（epoch）

- `accountChanged()` で `workEpoch += 1`（全消去・アカウントの選択と同じ）。止まった往復は `Interrupted` で 0 を返し、すぐ後ろに積んだ 1 周が確かめて status を決める。1.5 秒後の送信と再試行のタイマーは自分の epoch を持つので触らない（走るときに関門で確かめる）。
- 往復の epoch は `run` の頭（確かめの前）で取り、`pull(epoch:)`・`push(epoch:)`・`cloudErase(epoch:)`・`recoverFromZoneLoss(epoch:)` に渡す（自分で取り直さない。M1）。`run` の `do` の 1 行目（保留の全消去の前）と `ensureZoneAndSubscription()` の後に `checkEpoch`。`recoverFromZoneLoss` は `ensureZone` と `ensureSubscription` の後に `checkEpoch`。`cloudErase` は 1 行目で `checkEpoch`。全消去と取り込みの `Meta` は、関門の前に epoch を取る。
- 確かめの途中に `.CKAccountChanged` が来たら、その往復は確かめの結果を使わずに止まる（epoch が確かめの前に取ってあるため）。

### 3.5 止められた往復（M2）

- 裏にいるあいだ、往復が要求を出す直前（push の各ページの保存、pull の取得、全消去の一覧と各削除、`Meta` の保存）に `checkStillFresh()`: 最後に確定した確かめを**問い合わせた**時刻から 10 秒（`SyncEngine.awayRecheckAfter`）を過ぎていたら、確かめを頼んで 1 周を積み、`Interrupted` で止まる。iOS に止められた往復が、アカウントを切り替えた後に起きても、確かめなしに次のページを送らない（Apple アカウントの切り替えは 10 秒より長くかかるので、切り替えの後の要求はふつうは「古い」と分かる【未確認。実機では計っていない】。10 秒より速く切り替えた場合は `.CKAccountChanged` と epoch が頼り）。裏での普通の往復は確かめから 1〜2 秒で終わる【未確認。実機では計っていない】ので、呼び出しは増えない。
- **止められた場所が確かめの中のとき**（レビューの指摘で足した）: 裏に回るときの送信は、確かめ（`userRecordName()`）の答えを待つ間に止められることがある。答えが切り替えの前に出ていて、復帰の後に届くと、古い名前で「確定」してしまう。そこで `checkAccount()` は頭で問い合わせの時刻（`askedAt`）を取り、裏にいるあいだに答えまで 10 秒より長くかかったら、その答えを使わない（確かめを頼み直し、backoff の再試行に回して false）。確定したときに記録するのも答えの時刻ではなく `askedAt`。すぐにやり直さず backoff に回すのは、裏で遅い確かめのたびに待ち無しで繰り返さないため。前面では何も変わらない（test53）。
- 前面への復帰が先に来た場合は、§3.3 の epoch で止まる。

### 3.6 ゾーン消失・トークン切れ・記録の消失（M3）

確かめが待っているあいだ（裏にいるときは必ず）に `zoneMissing`（`run` と `fetchPage`）・`changeTokenExpired`（`pull`）・`recordNotFound`（`push`）が来たら、後始末（全部を送り直す・全部を取り直す・新しい記録として送る）の前に `confirmAgainIfDue(epoch)` で確かめる。確定しなければ `Interrupted`（status と再試行は確かめが決める。`handleFailure` を二重に呼ばない）。前面で確かめが待っていないときは今のまま（test16・test12・test31 の呼び出しの並びは変わらない）。

### 3.7 「手書きを残して使い始める」

### 4.2 仕組み（診断のとおり）

- **1 つ目**: `TestSleeper.advance()` は止まっている sleep（15 秒の再試行と 1.5 秒の送信）を一度に全部起こします。起きたタスクは協調スレッドプールを通って MainActor に戻るので、**戻る順番は起こした順に決まりません**。送信が先に戻ると、直列の待ち行列が「送信 → 取得」の順になり、送信の成功で「同期済み」、続く取得の失敗で「オフライン」になります。テストは「取得 → 送信」の順を前提にしていました。

## 11. 既定で決めたこと・確かめていないこと

### 11.1 既定で決めたこと

1. `.inactive`（コントロールセンター・アプリの切り替え画面・Apple のシート）では裏の印を付けない。iPhone と全画面の iPad では、アカウントの切り替えに「設定」アプリを開くので `.background` を通る（Split View・Slide Over・Mac で通らない場合は §11.2。そのときは `.CKAccountChanged` の epoch で止まる）。
2. 裏にいるあいだは、往復ごとに毎回確かめる（費用は §1.2）。裏でした確かめが成功しても印は下ろさない。
3. 「手書きを残して使い始める」を選んだら、前のアカウントで保留になっていた iCloud の全消去を取りやめる。アカウントを切り替えた直後に全消去を押し、その後「残して使い始める」を選んだ人には、新しいアカウントの手書きが端末に戻ってくる（もう一度消せば消える）。他人の iCloud を消してしまうより、取り返しのつく方を既定にした。
4. 全消去の iCloud の分は確かめの後。確かめられない・途中で変更が来たときは、端末の分だけ消して「iCloud の手書きを消せませんでした…」のお知らせを出す。同じアカウントなら、すぐ次の同期が保留の削除を済ませるので、**お知らせと実際がずれることがある**（文言は変えない）。
5. サイレントプッシュでも毎回確かめる（前面でも）。場面の知らせを取りこぼしたときの保険。費用は §1.2。
6. 裏で最後の確かめから 10 秒を過ぎた往復は止まって確かめからやり直す。裏で答えまで 10 秒より長くかかった確かめは使わず、backoff の後に確かめ直す（§3.5）。
7. テストの `advance()` は「始まった順」に起こす（実時間の締め切り順ではない）。今のテストはこの順を前提に書かれている。
8. CI の繰り返しは 20 回（計画の 25 回から減らした。ジョブの時間の上限のため。§4.4）。
9. 新しいテストの名前に番号（test37 など）は付けず（名前で呼ぶ）、M4_CONTRACT §8.2 の表で 37〜53 と対応させた。
10. 批評の「`appear()` でも前面を知らせる」を入れた（§3.3）。入れないと、初めから `.active` で現れた起動では、最初の前面のあいだずっと 1 ページの取得が省かれ、送信のたびに確かめが増えるため。両方が来ても、2 回目の `syncNow` は待っている 1 周を共有するか、取得が 1 回増えるだけ。

### 11.2 確かめていないこと・残る穴

- 本物の CloudKit での順番（停止からの復帰・期限の過ぎたタイマー・`.CKAccountChanged`・サイレントプッシュ）。偽物の DB のテストと §9 の普段の同期の確かめで代える。
- **送信中の 1 件**: `.CKAccountChanged` が届く時刻はエンジンには変えられないので、知らせの前に出した 1 件の保存は新しいアカウントに届きうる。その 1 件も「送っていない」印のまま残り、「残して使い始める」なら送り直され、「消して使い始める」なら消える。
- iPad の Split View・Slide Over で「設定」を並べて切り替えると、このアプリは裏に回らない。そのときはアプリが動いたままなので `.CKAccountChanged` がすぐ届き、epoch で止まる。
- Mac（iPad のアプリとして）では停止が無く、システム設定で切り替える間に窓が見えていると `.inactive` のままで `.background` にならないことがある。この場合も `.CKAccountChanged` と epoch だけが頼り。
- 裏での確かめの 10 秒（§3.5）: 問い合わせから 10 秒以内に答えと停止と切り替えが全部収まった場合は、この守りでは分からない（`.CKAccountChanged` と epoch が頼り）。10 秒という長さが実機で十分かは【未確認。実機では計っていない】。
- 裏で一度も前面に出ない起動では、印が下りないので、どの往復も確かめる（呼び出しが増えるだけ）。
- CI のシミュレータで 20 回回しても、負荷が無ければ古い仕組みでも赤が出ないことがある（§4.4）。
- `TestSleeper` の「着いた」合図は、`sleep` の終わりから `pause` の `beginJob()` まで MainActor を手放さないことに頼っている（型で支えている）。外れればまた揺れになるが、20 回の段で見つかる見込み。
