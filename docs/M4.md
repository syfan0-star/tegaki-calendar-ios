# M4 の実装結果（iCloud 同期、Web 版からの手書きの引っ越し）

[M4_CONTRACT.md](M4_CONTRACT.md) の契約を実装した結果のまとめです。設計の根拠は [DESIGN.md](DESIGN.md)（§2.8 設定画面、§2.10 初回案内、§3.4 線の id と所属マス、§3.9 保存形式、§5 同期、§6 Web 版からの移行、§8 技術構成、§9 段階計画、§10 審査）。[M3B.md](M3B.md) の続きで、M2・M3a・M3b で出来ていたこと（4 ページ・手書き・予定の読み書き・投げなわ・設定画面）はそのまま生きています。
ブランチ `m4`（iPad アプリ）と、Web 版リポジトリのブランチ `m4-export`（1.0.6。未プッシュ・未マージ）。`main` への取り込みと GitHub Pages の更新はリード（本人）が行います。

本人の決定どおり: 同期は CloudKit のプライベートデータベース（コンテナ `iCloud.com.syfan0.tegakicalendar`、専用ゾーン `tegaki`、1 ページ = 1 レコード `InkPage`、本文は常に CKAsset）、保存は `.ifServerRecordUnchanged` で衝突したら merge して再保存（最大 3 回）、差分取得は変更トークン、ページを開いたときはそのページだけ個別取得、サイレントプッシュ、1.5 秒デバウンス、再試行は 15 秒から倍々で 5 分まで。**端末内ファイルが常に主** で、iCloud は「ほかの端末へ届ける経路」と「バックアップ」。「この iPad の手書きを全て消す」は iCloud のレコードも消す。スキーマは本人が CloudKit Console で作って Production に配備する（§2.3）。版はアプリ **0.5.0**、Web 版 **1.0.6**。

### 2.3 本人がやること（Claude が代行できないこと）

#### (1) Apple Developer サイト（Certificates, Identifiers & Profiles）

1. **Identifiers › iCloud Containers** で `iCloud.com.syfan0.tegakicalendar` を作る。
2. **Identifiers › App IDs** の `com.syfan0.tegakicalendar` を開き、Capabilities に **iCloud**（CloudKit にチェックし、上のコンテナを割り当てる）と **Push Notifications** を付けて保存。
3. **Profiles** で App Store 用のプロビジョニングプロファイルを **作り直す**（Capabilities を変えると古いプロファイルは無効になる）。ダウンロードして base64 にし、GitHub のリポジトリ → Settings → Secrets and variables → Actions の `BUILD_PROVISION_PROFILE_BASE64` を更新する（古いままだと `testflight` の archive が entitlements の不一致で失敗する）。

| `recordName`（システム） | — | — | **QUERYABLE（推奨）**。アプリの動作には不要だが、Console の「Query Records」でレコードを見るのに要る |

**`Meta`**（recordName = `"meta"`。1 件だけ）

| フィールド名 | Console の型 | 中身 | インデックス |
| --- | --- | --- | --- |
| `schema` | Int(64) | 1 | 不要 |
| `webImportedAt` | Date/Time | 「Web 版の手書きを取り込む」が成功した時刻 | 不要 |
| `trialStartedAt` | Date/Time | M5 が書く（無料試用の開始）。M4 は読み書きしない | 不要 |
| `app` | String | `"ios/0.5.0/1"` | 不要 |
| `recordName`（システム） | — | — | QUERYABLE（推奨。同上） |

手順: Record Types の「＋」で型名を入れ、Fields にフィールド名と型を 1 つずつ足して保存 → Indexes で `recordName` に QUERYABLE（と `updatedAt` に SORTABLE）→ 2 つとも出来たら画面上部の **「Deploy Schema Changes…」** で Production に配備（差分の確認画面で Deploy）。アプリは CKQuery を使わないので、索引を忘れてもアプリは動きます。

**配備を忘れたときの症状**: Production にレコード種別が無いと保存・取得が `invalidArguments` / `serverRejectedRequest` 系で失敗し、ヘッダーが「エラー」、設定の「同期」が「同期に失敗しました」と footer にその文（自動再試行はしない）。Console で Deploy してから設定の「今すぐ同期」を押せば直ります。

#### (3) TestFlight

GitHub の Actions → `testflight` を手動実行（Secrets の更新後）。処理が終わったら TestFlight の iPad と iPhone で §2.4 の表を確かめる。

#### (4) Web 版の公開

Web 版リポジトリのブランチ `m4-export`（コミット `8de2bab`、`npm test` 609 本緑）はまだプッシュもマージもしていません。アプリ側の取り込みがこの書き出し（同じ見本）を読めることは CI で確かめてあるので、`main` にマージして GitHub Pages を更新し、設定の「手書きを書き出す（iPad アプリ用）」が iPad の Safari で JSON を保存できるか手で確かめてください（iPad Safari はダウンロードの設定次第で JSON をその場で開くことがあります。その場合は共有 → 「ファイルに保存」）。

### 2.4 iPad で（TestFlight に入ってから）

使い方:

1. iPad で iCloud にサインインしていれば何もしなくても同期が始まります。ヘッダー右の **☁** が「保存済み」なら iCloud にも入っています（書いてから 1.5 秒 + 1.5 秒で送られる）。「同期中」は送っている途中、「オフライン」は回線が無い（戻れば送る）、「この iPad のみ」は iCloud にサインインしていない、「エラー」「停止中」は設定の「同期」に理由が出ます。☁ をタップすると設定画面。
2. もう 1 台（iPhone でも）で同じ Apple ID でアプリを開くと、同じ手書きが見えます。相手が書いた線は、**アプリを前面に戻したとき** と、ページを開いたとき、サイレントプッシュが届いたときに取り込まれます（5 秒以内。プッシュは届けば自動、届くことは保証しない）。
3. 設定 › データ › 「Web 版の手書きを取り込む」: Web 版の設定で「手書きを書き出す（iPad アプリ用）」をして「ファイル」アプリに入った `tegaki-web-export-YYYY-MM-DD.json` を選びます。進捗の後に「Web 版の手書きを取り込みました（n ページ・m 本）」。同じファイルをもう一度取り込んでも増えません。
4. 設定 › データ › 「この iPad の手書きを全て消す」は、iCloud が使える状態なら iCloud のレコードも消し、ほかの端末からも消えます（2 回確認）。
5. 別の Apple ID でサインインし直すと「別の iCloud アカウントです」と聞かれます。「手書きを残して使い始める」なら全ページが新しいアカウントの iCloud へ送られ、「手書きを消して使い始める」なら空から始まります（もう一度確認）。「あとで」なら同期を止めたまま（次の起動でまた聞く）。
6. 初回案内は 4 枚になり、4 枚目が「iCloud と手書きの保存」。許可の画面は 4 枚目のボタンで出ます。

**実機で確かめること**（CI のシミュレータでは確かめられないもの。契約 §9）:

| # | 確かめること | 期待 |
| --- | --- | --- |
| 1 | iPad と iPhone で同じ手書きが見える | 書いて 5 秒以内に相手の **前面復帰** で届く（サイレントプッシュは届けば自動） |

## 4. 既知の制限・確認待ち

### 4.1 契約からの小さなずれ（意図したもの）

TegakiKit（K）:

- `WebImport` に契約に無い公開メンバーを足した（追加のみ。契約の型・シグネチャは不変）: `Stroke.Tool.defaultColor` / `.defaultSize`、`defaultPenSize` / `defaultHighlighterSize` / `minSize` / `maxSize` / `maxCoordinate`、`normalizeSize(_:tool:)`、`normalizePoints(_:)`（Web 版 `normalizeSize` / `normalizePts` の写し。KitChecks と XCTest が直接検査する）。`Point` / `Stroke` / `Page` / `Document` / `Skipped` / `Conversion` に public のメンバーワイズ init。`SyncState` に全引数既定値付きの public init。`SyncBackoff.maxFailures = 30` を public static let に。
- `WebImport.parse` は `v` が欠けている・数値でないときは 1 とみなす（契約は v > 1 だけを拒む理由にしている）。`strokes` が object でなく配列でも読む（Web 版 `deserializePage` と同じ）。`pages` の object でない要素・`pageId` の無いページは解析では落とさず、`convert` で `.unknownPageId` として skipped に入る。
- `InkPage.contentDiffers(from:)` は `unknownStrokes`（この版が知らない tool の線）の id も生きている線に数える（新しいアプリの線を同期の差分判定で無視しないため）。`liveStrokeIds` は契約どおり既知の tool だけ。
- KitChecks の追加は 419 項目（契約の目安 約 225 より多い）。`sync state (M4)` 節に §3.6 の検査 17 項目を含む。

同期エンジン（S）:

- `CloudKitDatabase` と `InMemoryCloudDatabase` は `@MainActor` の class（プロトコル `CloudDatabase` は非隔離のまま）。同期的な要件 `subscriptionID(in:)` と `accountChanges`、`CloudKitDatabase.init` と static の定数は `nonisolated`（`SyncEngine.live` の既定引数のため）。`InMemoryCloudDatabase.Operation` は `Hashable`、偽物に `fetchChangesNamesOnly: [Bool]` を追加（テスト用）。
- `SyncEngine` の内部メンバー（テストから見える）: `state`、`stateStore`、`stateSaveFailed`、`demoLastSyncOffset = 180`。`start()` は毎起動必ず 1 回アカウント確認をする（アプリを閉じている間のサインアウトは `.CKAccountChanged` が来ないため）。
- `start()` 前の `save` は dirty をメモリにだけ持ち（状態ファイルは `start()` が読むまで書かない）、`start()` が合流させる。`onRemoteUpdate` は常に呼び（表示中かどうかは画面が見る）、`deletedNames` では `InkPage.empty` で呼ぶ。
- デバウンス後の push と push 直後の「もう 1 周」は pull をしない push だけの仕事として同じ直列の待ち行列に積む。`pageOpened` の個別取得も同じ待ち行列を通る。
- 失敗の扱いで契約が空けていたところ: `limitExceeded` がこれ以上割れない → `.error(.server("limit"))` と backoff、同じページの 2 回目の `recordNotFound` → `.error(.server("record"))`、2 回目の `zoneMissing` → `.error(.server("zone"))`、`fetchPage` の `networkUnavailable` は同じ経路で `.offline` と backoff、`ensureZone` / `ensureSubscription` の失敗はその周では無視（pull が問題を報告する）。保留中の全消去でゾーンが無い（`zoneMissing`）ときは「消すものが無い」として `pendingCloudErase` を下ろし、次の周でゾーンを作り直す。
- `eraseEverything()` は `localOnly` / `accountMismatch` では `cloudPending` を false で `resetAfterErase`（iCloud の削除を保留にしない。別アカウントのレコードを後で消さないため）。
- `Meta` の seen は `state.seen["meta"]` に持つ。`saveMeta` は衝突 3 回・`recordNotFound` 1 回まで再試行。pull では `Meta.webImportedAt` が non-nil のときだけ state に写す。
- `importPages` の `strokesAdded` は「merge 後に生きていて取り込み前には無かった id の数」（取り込んだ墓標で消えた線は引かない）。ページごとに 1 回 yield して進捗を描かせる。
- `CloudKitDatabase.retryAfter` は `CKErrorRetryAfterKey` を `NSNumber` として読む。`partialFailure` の写像は `serverRecordChanged` の項目を優先し、次に `unknownItem` 以外の項目。
- 契約に無いテスト: `testStatusWording`（§6.1 の表全部）、`testEraseWhenTheZoneIsGoneHasNothingToDelete`、`testInkPageStoreListsItsPages`、レコード・Asset の変換と `clearUploadDirectory` のテスト。

画面（U）:

- `PageHeaderView` の `sync` / `onSyncTap` には既定値（nil / 何もしない）がある。`CalendarRootScreen` は常に `sync.snapshot.status.header` を渡す。
- 全消去の文言: `.accountMismatch` は `localOnly` と同じ扱い（「この iPad に保存した手書きを全て消しますか？」。エンジンもその状態では iCloud を消さない）。`SettingsScreen.erasesCloud(_:)` / `canSyncNow(_:)` は static のヘルパー。
- `WebImportSheet`: `interactiveDismissDisabled` は `.reading` でも有効（契約は「取り込み中だけ」）。`.reading` は不定の `ProgressView` と「取り込んでいます…」、`.importing` は「取り込んでいます… {done} / {total} ページ」。解析と変換は `Task.detached` で（大きなファイルでシートが止まらない）。`Data(contentsOf:)` の失敗は「ファイルを読めませんでした」。トーストは `.done` のときだけ。`.presentationDetents([.medium])` は iPad でも付けたまま（iPad は無視する）。
- アカウント切替の問い合わせ: `onChange` に加えて `appear()` でも、既に `.accountMismatch` なら出す（エンジンの 1 周目が画面より先に終わることがある）。シートが出ている間は保留し、閉じて 0.35 秒後に出す。「新しいアカウントで使い始める…」は設定を閉じてから。`.keepInk` の前に `saveNow()`（最後の 1 本も一緒に送る）。答えた後は表示中のページを `sync.load` で読み直す。
- `ScreenshotMode.Sheet` の `import` はバッククォート付き（予約語）。`settings` と `sync` はどちらも設定画面を見本のエンジンで出すが、`sync` だけ `SettingsScreen` の `scrollToSyncOnAppear: true`（契約 §6.2 の引数に足した既定値 false の引数。`CalendarRootScreen` が `ScreenshotMode.current?.sheet == .sync` のときだけ true を渡す）で開いた 0.4 秒後に「同期」の節へスクロールする（`ScrollViewReader` と最初の行の `.id`。1 回目の CI の `sheet-sync.png` が「カレンダー」の節しか写していなかったため）。スクリーンショットモードの全消去はページを空にするだけでトーストは出す（M3b と同じ）。
- `AppDelegate` は明示的に `@MainActor`、登録の失敗は `os.Logger` で記録。
- `InkLedgerTests` の §8.3 (2) と (3) は 1 本のテスト（墓標にした線と遠隔の線の両方を 1 回の reload で）。`ScreenshotModeTests` の追加は 2 本。

Web 版（W）:

- `exportInkFlow` は `onProgress` をトーストに渡さない（トーストの文言を更新する API が無い。「手書きを集めています…」が終わるまで出たまま）。
- お試しモードでは `includesDemo: true` で書き出す（ファイルにはお試しの手書きしか無いため）。Google モードでは `includeDemo` のチェックどおり。
- Google の期限切れ（`AuthRequiredError`）はオフライン扱いにせず「書き出せませんでした: Googleに再接続してください」。オフラインの判定は回線の誤り（status 0）だけ。
- 設定の結果は常に `includeDemo` を持つ（チェックが無いときは false）。チェックの表示条件は `signedIn && !demo`（排他なので動作は契約と同じ）。

統合（C）:

- `PrivacyInfo.xcprivacy` は契約 §8.4 のとおり `Sources/TegakiCalendar/` に置いた（`sources` がフォルダごとなのでリソースとして入る）。
- `build.yml` の KitChecks のステップは件数を表示してから `test -ge 20400`。それ以外の手順は M3b のまま。

### 4.2 実機でしか確かめられないこと

- 本物の `CKDatabase` の往復（§2.4 の表 9〜15）。`CloudKitDatabase.swift` は Catalyst SDK に対する型検査と `map` の XCTest だけで、往復は実機が初めて。特に push の衝突で `CKRecordChangedErrorServerRecordKey` の CKRecord に `doc` の Asset が付いて来ること（付いて来なければ端末内の版でサーバー版を上書きする。相手の線は相手の次の pull/push で戻る）。
- サイレントプッシュの配信とバックグラウンド起動、`.CKAccountChanged` の実際の通知、容量不足、ゾーンの削除、Production にスキーマが無いときの文。
- `encodeToken` / `decodeToken`（`CKServerChangeToken` は手で作れない）。
- 「ファイル」アプリが Web 版の書き出しを JSON でなくテキスト扱いにするときの選択（`.plainText` も開けるようにしてある）。
- Web 版の `Blob` + `<a download>` が iPad の Safari で保存できるか（ダウンロードの設定次第）。
- iPad の `confirmationDialog` はポップオーバーになり「あとで」（cancel）が隠れる。外をタップして閉じると `onChoose(.later)` は呼ばれない（エンジンにとって `.later` は何もしないので動作は同じ）。

### 4.3 動作上の注意

- 端末内が主。iCloud から線が消えても端末内に残っていれば送り直す（他端末の全消去の後にこの端末で書いた線は新規として iCloud に戻る）。他端末の全消去で消えたページは `deletedNames` でこの端末からも消える。
- 同期の「差があるか」は `contentDiffers`（線の id の集合と墓標の集合）で見る。`updatedAt` だけの違いでは何もしない。
- 画面のデバウンス 1.5 秒 + エンジンのデバウンス 1.5 秒で、書いてから約 3 秒で iCloud へ（M4-11）。
- 取り込んだ線の `dev` は `"web"`、`dtMs` は 8 ms 刻み。Web の点は「ならした通過点」なので PencilKit の線はわずかに内側を通る（画面上 1 px 未満。DESIGN §6.4 で許容済み）。月ページで複数のマスにまたがる長い線は、外接矩形の中心のマスに入る（相対座標が負や 200 超になるが描画はそのまま）。
- 別の端末が消した線の undo は新しい id の複製として戻る（M2 の規則。仕様）。
- アカウント切替の問い合わせに「あとで」と答えると `.accountMismatch` のまま（ヘッダー「停止中」）。次の起動でまた聞く。
- 設定の「同期」「データ」は本物に、「購入」は準備中のまま（M5）。「手書きを書き出す」（アプリから）も M5 以降。
- M5 以降に残すもの: 課金・閲覧専用モード（`Meta.trialStartedAt` は項目だけ用意済み）、アプリからの手書きの書き出し（JSON・PDF・画像）、設定の同期、墓標の掃除、キャンバスの使い回し（DESIGN §3.10）。

### 4.4 技術的な注記

- 言語モードは Swift 5・並行性チェックは minimal のまま。`SyncEngine` は `@MainActor`。CloudKit を import するのは `Sync/CloudKitDatabase.swift` だけ。`Sync/*` は `Views/*` に依存しない。
- `SyncEngine.shared` の分岐: スクリーンショットモードと XCTest のホスト（`NSClassFromString("XCTestCase")` か XCTest の環境変数）では不活性な見本（偽物の DB、ファイルも触らない）、`--no-icloud` は偽物の上の本物、それ以外は CloudKit。`CKContainer` は最後の分岐で最初の呼び出しのときに作る。
- `CalendarRootScreen` の `@ObservedObject private var sync = SyncEngine.shared` は View のプロパティ初期化子で main-actor の static に触るので、Swift 5 モードでは警告、Swift 6 モードに上げるときは直す。
- `SyncEngineTests.waitUntilIdle` は `Task.yield()` 3 回で `TestSleeper.advance()` と account-change のストリームから再開した Task が先に走ることに頼る（macOS の Swift 6.4 ランタイムと CI のシミュレータで通る。FIFO は形式的には保証されない）。
- `SyncEngineTests` の 0（ホストが `CKContainer` を作らない）は、ホストアプリがテストバンドルの読み込み前に `SyncEngine.shared` に触らず、XCTest の環境変数があることに頼る。
- この Mac には Xcode が無いので、本番のコンパイルは CI。手元では TegakiKit の `swift build` / `KitChecks`、全ファイルの `swiftc -parse`、アプリ全体の Catalyst SDK に対する型検査（SwiftUI の `@State` は CLT にマクロのプラグインが無いので同じ形のラッパーに置き換えて）、XCTest の代役に対するテストの型検査、同期エンジンのテストの macOS での実行まで。
