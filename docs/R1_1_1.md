## 2. 原因

**上の空白は、紙を上下の中央に置いていたことです**（`ZoomPolicy.centeringInsets`。M4c から）。予定や手書きの少ないページは紙が画面より短くなり、上下に机の色の余りが出ていました。**大きさの違いは、開く倍率を「そのページ全体が入る倍率」で決めていたことです**（`ZoomPolicy.overviewSize` は年では紙全体で、予定と手書きで伸びる）。行が多い年ほど縮めて開くので、年ごとに大きさが変わっていました。

ただし iPad の上の空白は、この見立てでは一部しか説明できません（§2.3）。

## 3. 直したこと

（作業のときの案の名前 (a)〜(e) は、§3.1〜§3.5 に当たります）

### 3.1 紙は上寄せ（`ZoomPolicy.centeringInsets`、`InkCanvasView.applyInsets`）

`centeringInsets` の height を常に 0 にしました（横の中央寄せは残す）。キャンバスの余白は上 0、左右は中央寄せの分、下は丸ボタンの `bottomClearance`。余りは紙の下に残ります。

### 3.2 開く倍率を基準の紙で決める（`ZoomPolicy.baseSize`・`Bounds.open`、`InkCanvasView`）

- 基準の紙: 月 1400 × 1050、週 1400 × 1920、日 1000 × 2400、年 1400 × 1860。予定や手書きの量で変わらないので、同じ端末ならどの月もどの年も同じ大きさで開きます。
- 最小倍率は今までどおり一覧（そのページ全体が入る倍率）。`overviewSize` は必ず基準以上なので式は変えていません。つまんで縮めればページ全体が見えます。
- 保存する比率は「開く倍率に対する比」です。1 未満は保存しません。**基準の紙のページでは 1.1 と同じ値なので移し替えは要りません**（伸びたページでは、前に拡大していた端末は次にピンチするまで前より大きく開きます。§6.4）。
- キャンバスの追い方: 開く倍率のままなら、回転と領域の高さの変化で新しい開く倍率へ。行が伸びても倍率は変わりません（**書いている紙が縮まなくなりました**）。つまんで下限にしているときは、回転では新しい下限へ、行の伸び縮みでは追いません（高さが増えて下限が上がり、下限の外に出たときだけ新しい下限へ上げます）。拡大中は今までどおり絶対倍率。
- **回転と高さの変化で倍率が変わるとき、紙の上端を保ちます**（開く倍率か下限のとき）。今の手順は画面の中央の点を保つので、紙が長くなると一番上にいても上端がずれます（計算で iPhone 18 Pro Max の横→縦、月 78 pt、日 547 pt、伸びた年 166 pt）。これは「紙はいつも画面の上から始まります」と食い違うので、§3.1 と一緒に直しました。

### 3.3 メモ欄を最初から全開（`PaperGrowth.tailHeight`、`PDFPageRenderer.paperRect`）

- 月のメモ欄と日の「自由メモ」は最初から 6,000 lu（`max(growMax, b + 50)`）。1.0 の線が上限より下にあっても見える `b + 50` の規則は残します。高さは計算の結果で保存しません（K-5）。1.1.1 で深く書いた線は 1.0 でも 1.1 でも見えます。
- 書いても再レイアウトが走らなくなります（b ≤ 5,950）。軽い経路は b > 5,950 のときだけ通ります。1.0 の深い線のほか、**自分の端末の線でも通ります**: 下端の近くに書いた線（捨てるかどうかは線の中心で決めるので、中心が 6,000 より上でも b は 5,950 を超える）と、投げなわで下端へ動かした線（`clampedMoveDelta` は `pageSize` で止めるだけで `drop` を通らない。何も書いていない月でも、引くたびに 50 lu ずつ伸びる）。線は消えず 1.0 でも見えるのでデータの害はありません（止めない理由は §8 の 9）。「メモ欄はここまでです」は今までどおり b > 5,600 と上限より下の線で出ます。
- **PDF は 1.1 の長さのままです**。メモ欄に 1 本でも書いてあると紙全体を使っていたので、そのままだと 1400 × 7,050 lu 以上に膨らみ、手書きの画像も 12M 画素の上限で粗くなりました。PDF には 1.1 の段の式（`PaperGrowth.exportTailHeight`）を使います。1.0 の深い線は `b + 50` で入ります。

### 3.4 ピンチの案内（`CalendarRootScreen`）

- 文: 「2 本の指を広げると拡大、つまむと縮小します」（6 秒、既存のトースト）。つまむのは縮小で、予定の少ないページは開いた倍率が下限なので、「つまむと拡大・縮小」だと、つまんでも紙が跳ね返るだけで効かないと見えます。本人の「ピンチイン、アウト」の両方向を文に出しました。
- 端末ごとに一度だけ（`hint.pinchShown`）。開いて 4 秒後（最初の購入画面が出る時間の後）。シート・初回案内・アカウントの質問・別のトーストと重なるときと、アプリが裏にあるときは出さず、次の機会（シートを閉じた、前面に戻った、次の起動）にまた待ちます。
- 既にピンチで拡大したことがある人（保存した比率がある人）には出しません。**ただし TestFlight と審査の版（サンドボックスのレシート）では出します**。本人はもうピンチしているので、この例外が無いと本人の実機で一度も見られません。App Store の版では効きません。
- 待っている間に本物のピンチが来たら、もう出しません。写真モードと XCTest の中では出しません（`pinchHintDue`）。写真は `--screenshot-pinch-hint` で撮ります。

## 10. 契約からのずれ

契約の第 2 版からのずれです。K の分は §5.1 の末尾にあります。

| # | ずれ | 理由 |
| --- | --- | --- |
| 1 | `containerDidLayout` の手順 4 と `applyBounds` で、古い offset（`topY`・`centerPaper`）を **`minimumZoomScale` の代入の前** に読む。`applyBounds` の「倍率が変わるか」も代入の前の倍率で判定する | UIKit は下限の代入で倍率と offset を動かすことがあり、この Mac だけでは iOS の動きを測りきれない。動いても動かなくても同じ結果になる形にした（契約 §2.2 の「最初から同じ形にする」の考えを 1 歩進めた） |
| 2 | テストの名前を変えた: `testMonthRowGrowthLowersTheOverviewZoomInLandscape` → `…KeepsTheOpeningZoomInLandscape`（契約どおり）、`testNeedsMoreRoomFollowsTheStepRule` → `…TheOpenTailRule`、`testParseEmpty` → `testParseEmptyAndPinchHint`（commit 0 の物に足した） | 中身が名前と合わなくなるため |
| 3 | `StickyHeaderView` は変えていない | 契約の「確かめた消費者」のとおり、`offsetX`・`zoom`・`width` だけ読むので直す所が無い。注記の「centred」も横の話で今も正しい |
| 4 | `testTodayOpeningAPageBringsTheRowOnScreen` に丸ボタンの余白の確かめを足した。`testTallYear…` に空の年との比べ合いを足した | `reveal` の `bottomClearance` を引く所を通すため |
| 5 | `HeaderAndPaperUITests` の「年表示」は `app.buttons` でなくラベルで探す | SwiftUI の分段の部品がどの種類の要素に見えるかをこの Mac で確かめられない。場所が読めればよい |
| 6 | README の表の行「一覧とピンチ」を「開く大きさとピンチ」に変えた。版の行・数も直した | 今は開く倍率と一覧が別の物なので |
