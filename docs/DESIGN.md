## 1. 目的と方針

紙の手帳のように、iPad の「カレンダー」に入っている予定の上へ Apple Pencil で自由に書き込めるアプリを、App Store で販売します。
Web 版（Safari で動く版）で確かめた使い勝手を、iPad のネイティブの部品で作り直します。

### 1.1 決定事項（2026-10-11、本人の決定）

| 項目 | 決定 | 理由・補足 |
| --- | --- | --- |
| 販売形態 | App Store で **個人として販売**。販売者欄に戸籍上の氏名が出ることは承知のうえ | 法人化は個人アプリ 1 本には重すぎる |
| 予定の読み書き | **EventKit**（iPad の「カレンダー」アプリと同じデータ）。Google の API・OAuth・Drive は **一切使わない** | Google の審査（未検証 100 人上限、独自ドメイン、英語の動画）が丸ごと不要になる。Google カレンダーは iPad の設定でアカウントを追加すれば同期される |
| 手書きの同期 | **CloudKit プライベートデータベース**（利用者本人の iCloud） | 開発者側のサーバー費用ゼロ、開発者は中身を見られない（プライバシーの説明が簡単） |
| 料金 | **サブスクリプション**（月額・年額）。責任の範囲を利用規約とサポートページに明記 | 買い切りだと将来の OS 対応の費用が出ない |
| 配信地域 | **日本中心。EU は除外** | EU に出すと住所・電話番号の公開義務（DSA）が生じる |
| レイアウト | 週・月の **行が伸びて、終日予定を全件そのままの大きさで表示**（ページが縦にスクロール） | 本人の案。「全部見える」を最優先。手書きは日付のマスに紐付ける（§3） |
| Apple Pencil | **ダブルタップ／スクイーズでペン ⇄ 消しゴム**。iPad の設定で選んだ動作を尊重 | Web 版の「2 本指タップ」の代わり |
| Web 版 | **本人の個人用・デモ用として残す**。販売はしない | 移行ツールで Web 版の手書きを取り込める（§6） |
| 対応 OS | **iPadOS 17 以上**（§1.3） | |

### 1.2 Web 版との関係

```
  Web 版 (Safari / PWA)                    iPad アプリ版 (この設計書)
  ─────────────────────                    ─────────────────────────
  予定: Google Calendar API  ──┐           予定: EventKit (iPad のカレンダー)
  手書き: Canvas + 自前の描画   │ 一度だけ   手書き: PencilKit
  保存: Google Drive 非表示領域 ─┼─────────▶ 保存: 端末内 + iCloud (CloudKit)
  本人の個人用・デモ用          │ 書き出し   App Store で販売
                               └→ JSON ファイル → 「取り込む」(§6)
```

- 二つの版は **実行中には何も共有しません**（同じ予定を見ることはできます。Google カレンダーが iPad のカレンダーに同期されるからです）。
- 共有するのは **考え方** だけです。ページの種類（年/月/週/日）、月曜始まり、終日予定の全件表示、ペン/マーカー/消しゴム/投げなわ/予定の 5 道具、「投げなわで囲んで予定にする」、月ページのメモ欄、祝日の自前計算、「ストロークの集合の和集合＋墓標」という同期の考え方は、そのまま持ち込みます。
- Web 版の手書きは、Web 版に「書き出し」機能を足し、アプリ側の「取り込む」で一度だけ移します（§6）。

### 1.3 対応機種・OS

| 対象 | 方針 |
| --- | --- |
| **iPad（iPadOS 17 以上）** | **第一候補・本命**。Apple Pencil で書くことが主役 |
| iPhone（iOS 17 以上） | 同じアプリが動く（ユニバーサル）。**閲覧＋軽い編集**（予定のタップ編集、指での短いメモ）。月ページは小さすぎるので、iPhone では週・日ページを中心に。手書きの新規作成は iPad を案内 |
| Mac（Apple シリコン） | **「Designed for iPad」の自動提供**。App Store Connect で何もしなければ Mac App Store にも並ぶ。Mac には Pencil が無いのでトラックパッドで書く形になる。初版では特別な対応をしない（不評なら Connect のチェックを外すだけで取り下げられる） |

**iPadOS 17 以上にする理由**

1. カレンダーの「フルアクセス」を求める新しい仕組み（`requestFullAccessToEvents`）が iOS 17 からです。16 以下も対応すると、古い仕組みとの二重実装になります。
2. 画面の状態管理（Observation）、PencilKit の互換性指定（`PKContentVersion`）、Apple Pencil Pro のスクイーズ（17.5）が 17 系で揃います。
3. **古い iPad を切り捨てすぎない**ためです。iPadOS 17 は 2017〜2018 年の iPad（iPad 第 6 世代、iPad Pro 10.5 インチなど）まで動き、これらは全て Apple Pencil（第 1 世代）に対応しています。18 や 26 を最低にすると、この世代が落ちます。
4. App Store の提出要件（Xcode 26 以上でビルド）とは別の話で、Xcode 26 も 27 も最低 iOS 15 まで対象にできるので、17 は問題ありません。

### 1.4 初版でやらないこと

- Google 固有の機能（予定ごとの色、Google タスク、Google カレンダーの新規作成、ゲストへのメール通知）。EventKit の範囲外です。
- ファミリー共有（課金）。§7。
- 英語版。まず日本語のみ（日本中心の配信）。
- Mac 専用 UI（Mac Catalyst）。Designed for iPad の自動提供で様子見。
- 共同編集・他人との手書き共有。手書きは本人の iCloud の中だけ。

## 2. 画面構成

### 2.1 共通の骨組み

Web 版と同じく「上にヘッダー、真ん中に紙、下に道具」です。

```
┌──────────────────────────────────────────────────────────┐
│ ◀  今日  ▶   2026年10月          日 週 月 年   ＋予定  ☁ 保存済み  ⚙ │ ← ヘッダー
├──────────────────────────────────────────────────────────┤
│  月  火  水  木  金  土  日                                  │ ← 固定見出し（スクロールしない。手書き不可）
├──────────────────────────────────────────────────────────┤
│                                                          │
│   紙（ページ）                                            │ ← 縦にスクロール。ピンチで拡大。
│   ・罫線と日付（グリッド）                                   │    手書きはこの上に乗る
│   ・予定の帯・チップ                                        │
│   ・手書き（PencilKit のキャンバス）                          │
│                                                          │
├──────────────────────────────────────────────────────────┤
│        ✎ ペン  ▮ マーカー  ◻ 消しゴム  ◌ 投げなわ  ▭ 予定   ●●●●●●  ↶ ↷  │ ← ツールバー（浮いている）
└──────────────────────────────────────────────────────────┘
```

- **ペンは書く、指は動かす**。指はスクロール・ピンチ・予定のタップ。設定で「指でも書く」をオンにできます（iPhone と Mac では既定でオン）。
- 左右スワイプで前後のページへ。ヘッダーの ◀ ▶ でも移動。
- 縦横どちらの向きでも使えます。向きを変えると紙の幅が画面幅に合うように拡大率が変わるだけで、手書きの位置関係は変わりません（§2.2）。（M4c: 一覧で見ていれば新しい一覧に、拡大中なら倍率をそのまま保って新しい範囲に収めます。[M4C_CONTRACT.md D4](M4C_CONTRACT.md)）

### 2.2 ページの座標系と「行が伸びる」レイアウト

**論理単位（lu）**: 各ページは画面に関係ない固定の「紙の幅」を持ちます。Web 版と同じ数字にします（移行の計算が足し算だけで済みます）。

| ページ | 紙の幅 W (lu) | 列の構成 |
| --- | --- | --- |
| 月 | 1400 | 7 列 × 200 lu。6 週（42 日）固定。下にメモ欄 |
| 週 | 1400 | 左に時刻の帯 64 lu、7 列 × 190.86 lu |
| 日 | 1000 | 左に時刻の帯 72 lu、時間軸 72〜660 lu、右 660〜1000 lu は自由メモ欄 |
| 年 | 1400 | 左に日付の帯 56 lu、12 列 × 112 lu、31 行 |

表示倍率 = 画面幅 ÷ W（幅ぴったり）（M4b: 下限は max(幅ぴったり, 読める倍率)。幅ぴったりが読める倍率の 95 % 以上ならそのまま。[M4B_CONTRACT.md §1](M4B_CONTRACT.md)）。ピンチで拡大できます（最小 = 幅ぴったり、最大 = その 4 倍）。
**M4c（[M4C_CONTRACT.md §1](M4C_CONTRACT.md)）**: 基本の状態は **一覧**。最小 = 一覧（fitAll = ページの一覧矩形が紙の領域（固定見出し・終日帯の下、ツールバーの上）に縦横とも入る倍率。一覧矩形は 月 = 6 行の格子 1400 × memo.minY、週 = 24 時間 1400 × 1920、日・年 = 紙全体）、最大 = max(4 × 幅ぴったり, 2 × 読める倍率)。「読める倍率」は倍率を縛らず、文字の閾値としてだけ残る（readable 未満の文字は readable のときの lu を凍結して比例縮小、下限なし。罫線は画面上 1 pt のまま）。開くときの倍率は一覧に対する保存比率（`UserDefaults` の `zoomRatio.<種類>`、既定 1 = 一覧、ピンチの終わりにだけ書く）。紙 × 倍率が画面より小さければ机の色（#ecebe6）の余白で中央に寄せる（計算は常に紙全体）。iPad の月は幅ぴったり（0.73・0.60・0.53）のまま変わらない。週・月・年の指のダブルタップでその日の日ページへ。

**行が伸びる**: 紙の高さは固定ではなく、予定の数と手書きの量で決まります。「全部見える」を守るための中心の仕組みです。

```
月ページ（例）                       各行の高さ H_r
┌────┬────┬────┬────┬────┬────┬────┐
│ 28 │ 29 │ 30 │ 1  │ 2  │ 3  │ 4  │  ← 日付見出し 28 lu
│■■■■■■■■■ 出張  ■■■■■■■■■│    │    │  ← 終日レーン 1（複数日の帯）
│    │■ 歯医者 │    │    │    │    │  ← 終日レーン 2
│    │ 9:00 会議 │    │    │    │    │  ← 時間指定チップ
│   手書きの余白（最低 40 lu）          │
├────┼────┼────┼────┼────┼────┼────┤  H_r = max(175, 28 + 2×25 + 1×20 + 40, 手書きの下端+12)
│ 5  │ 6  │ 7  │ 8  │ 9  │ 10 │ 11 │
│   予定が無い週は基本の高さ 175       │  H_r = 175
├────┴────┴────┴────┴────┴────┴────┤
│ メモ                                │  ← メモ欄（高さ max(700, 手書きの下端+50)）
└──────────────────────────────────┘
```

行の高さの式（月ページの週 r）:

```
H_r = max( 基本高さ,
           日付見出し + 終日レーン数(r) × (レーン高 + 隙間) + 時間指定チップ数の最大(r) × チップ高 + 手書き最小余白,
           その行の手書きの下端 + 12 )
```

| 定数 | 月 | 週（終日帯） | 日（終日帯） | 年 |
| --- | --- | --- | --- | --- |
| 基本高さ | 175 | 60 | 60 | 60 |
| 日付見出し | 28 | 0（固定見出しにある） | 0 | 16（曜日の字） |
| レーン高＋隙間 | 22 + 3 | 22 + 3 | 24 | 18 |
| チップ高（時間指定） | 20 | —（時間軸に描く） | — | —（年は終日のみ） |
| 手書き最小余白 | 40 | 30 | 30 | 8 |
| 上限 | 1200 | 800 | 800 | 400 |

補足:

- 「終日レーン数」は、その週の終日予定（複数日の帯を含む）を Web 版と同じ詰め方（`allDayRowsForRange` 相当）でレーンに並べた数。
- 「時間指定チップ数の最大」は、その週の 7 日のうち一番多い日の件数。**時間指定の予定も全件チップで出します**（Web 版は「+n件」でした。本人の「全部見える」方針に合わせました。**要確認 B-1**）。
- 「手書きの下端」の項は、予定が減って行が縮むときに **手書きが行からはみ出さない** ためのものです（紙は伸びるが、書いたところより縮まない）。
- 行の高さが変わるのは **ペンを離している時だけ**（§3.5）。書いている最中に紙が動くことはありません。
- 日ページ・週ページの時間軸（24 時間 × 1 時間 80 lu = 1920 lu、日は 100 lu × 24 = 2400 lu）は伸びません。伸びるのは上の終日帯だけです。

### 2.3 月ページ

- 月曜始まり固定。6 週 × 7 日の 42 マス。前後の月の日付は薄く表示。
- 各マス: 左上に日付（日曜・祝日は赤、土曜は青）、その横に祝日名。終日予定は週をまたぐ帯、時間指定は「9:00 会議」のチップ。チップ・帯の色はカレンダーの色。
- 日付の数字を指でタップ → その日の日ページ。帯・チップを指でタップ → 予定の編集画面。
- グリッドの下に **メモ欄**（罫線あり、「メモ」のラベル）。メモ欄はひとつのマスとして扱います。
- 固定見出しは曜日の行だけ。
- 初期表示はグリッドの先頭。縦スクロールでメモ欄へ。

### 2.4 週ページ

- 固定見出し: 曜日と日付（タップで日ページ）、祝日名。
- 紙の上部: **終日帯**（7 マス、伸びる）。Web 版では固定見出しの中にあって書けませんでしたが、アプリ版では紙の一部にして **終日予定の横にも書ける** ようにします。（M4b: 固定見出しへ戻した。紙は 0:00 から。書けない）
- その下: 時間軸グリッド（0〜24 時、1 時間 80 lu）。時間指定の予定は Web 版と同じ重なり処理で列分割。今日は赤い現在時刻の線。
- 初期スクロール: 今日なら「今の 1 時間前」、それ以外は 7:00。

### 2.5 日ページ

- 固定見出し: 日付（曜日・祝日名）。
- 紙の上部: 終日帯（1 マス、伸びる）。（M4b: 固定見出しへ戻した。紙は 0:00 から。書けない）
- その下: 左に時間軸（72〜660 lu）、右に自由メモ欄（660〜1000 lu）。時間軸とメモ欄は **同じ高さで一緒に動く** ので、ひとつの領域として扱います。

### 2.6 年ページ（年間予定表）

- 12 列（1 月〜12 月）× 31 行（1 日〜31 日）。存在しない日（2/30、4/31 …）は斜線。
- 固定見出し: 「1月」〜「12月」（タップでその月ページ）。（M4b: 全機種で横スクロール、月の列 150 pt 以上。マスの見出しに日番号）
- 各マス: 左上に曜日の字（月火水…、日祝は赤・土は青。タップでその日ページ）、下端に祝日名。終日予定は右 55% に小さなチップで **全件**。行が伸びる（同じ日付の 12 か月のうち一番多い月に合わせる）。
- 時間指定の予定は出しません（Web 版と同じ）。
- 初期スクロール: 今日の行の 2 行上。

### 2.7 ヘッダーとツールバー

**ヘッダー**: ◀ 今日 ▶ ／ タイトル（「2026年10月4日(日) 体育の日」「2026年9月28日〜10月4日」「2026年10月」「2026年」）／ 日・週・月・年 の切替 ／ ＋予定 ／ 同期の状態（「保存済み」「保存中…」「未送信」「オフライン」「この iPad のみ」「エラー」）／ ⚙ 設定。

**ツールバー**（画面下中央に浮く、Web 版と同じ並び）:

| 道具 | 動き |
| --- | --- |
| ペン | 6 色 × 3 段階の太さ。筆圧で太さが変わる |
| マーカー | 4 色。半透明の太い線 |
| 消しゴム | 触れた線を **線ごと** 消す（Web 版と同じ。部分消しはしない） |
| 投げなわ | 囲んだ線を選ぶ → 「予定にする」「削除」「選択解除」のメニュー。選択範囲の中をペンでドラッグすると動かせる |
| 予定 | 時間帯（週・日）や日付（月・年）をなぞる → 予定の作成画面。既存の予定をペンでタップすると編集 |
| ↶ ↷ | 元に戻す／やり直す（書く・消す・動かす・予定にして消す、すべて対象） |

iPad の標準のツールパレット（PKToolPicker）は **使いません**。理由は §3.6。

### 2.8 設定画面

| 区分 | 項目 |
| --- | --- |
| カレンダー | 表示するカレンダー（アカウントごとにまとめて、色の丸とチェック）／ 予定の登録先（書き込み可能なカレンダーから選ぶ）／「カレンダーへのアクセス」の状態と、拒否されているときは「設定アプリを開く」ボタン ／ Google カレンダーを使う人への手順（§2.10 と同じ内容） |

## 3. 手書きの設計（最重要）

### 3.1 使う部品: PencilKit（PKCanvasView）

iPad 標準のメモアプリと同じ描画部品です。利点:

- Apple Pencil の低遅延描画、予測描画、ホバーのプレビュー、筆圧・傾きの処理が **自動**。Web 版で苦労した「座標が整数に丸められる」「線の段差をならす」問題が消えます。
- 線は **ベクター**（点の列）として `PKDrawing` に入っており、1 本ずつ取り出せます（`PKStroke`）。これが「マスに紐付ける」ための前提です。

PencilKit は「紙全体にひとつの絵」を扱う部品で、「行が伸びたら日付ごとに線を動かす」機能はありません。それをどう実現するかが §3.3〜3.5 です。

### 3.2 キャンバスと紙の重ね方

```
  画面
  ┌────────────────────────────────┐
  │ PKCanvasView（透明）           │ ← 一番上。Pencil の線はここに描かれる。
  │   contentSize = 紙の大きさ      │    自身がスクロールビュー:
  │   zoomScale   = 表示倍率        │    指のスクロール・ピンチ拡大はこれが担当
  │ ┌────────────────────────────┐ │
  │ │ 紙ビュー（罫線・日付・予定）  │ │ ← 下。PKCanvasView の
  │ │  offset と zoom を同期      │ │    scrollViewDidScroll / scrollViewDidZoom
  │ └────────────────────────────┘ │    で位置と倍率を毎回そろえる（公開 API のみ）
  └────────────────────────────────┘
```

- **決定**: `PKCanvasView` を紙のスクロールビューそのものとして使い、罫線・予定は **別のビューを下に敷いて** スクロール位置と倍率を同期させます。
  - 理由: PencilKit は自分の `zoomScale` に合わせて線をくっきり描き直します。外側に別のスクロールビューを置いて拡大すると、線がぼやけたり、Pencil の入力と指のスクロールの奪い合いが起きたりします。
  - 「`canvasView.subviews[0]` に背景を差し込む」という裏技（内部構造に依存）は使いません。
- `drawingPolicy = .pencilOnly`（指は描かない）。「指でも書く」オンで `.anyInput`。
- 指のタップで予定を開く: `UITapGestureRecognizer` を PKCanvasView に付け、`shouldReceive touch` で `touch.type == .direct`（指）のときだけ受ける。タップ位置を紙の座標（`location ÷ zoomScale`）に直し、**自前の当たり判定**で予定の帯・チップを探す（Web 版の `elementFromPoint` と同じ発想）。予定ビューを UIKit のボタンにする必要はありません。
- 背景は紙色（#fffdf8）、キャンバスは透明。ダークモードでも紙は紙色のまま（PencilKit の自動色反転は切る）。

### 3.3 インクを「マス」に紐付ける方式の比較と決定

行が伸び縮みしても手書きが日付からずれないようにするには、線を「紙の座標」ではなく「マスからの相対位置」で持つ必要があります。二つの案を比べました。

| 観点 | **案 A: ページ全体で 1 枚のキャンバス。線ごとに所属マスを持ち、マス座標で保存。レイアウトが変わったら各線を平行移動して合成し直す** | 案 B: マスごとに PKDrawing（または PKCanvasView）を持ち、表示時に並べる |
| --- | --- | --- |
| マスの境界をまたぐ線 | 紙と同じ。自由に書ける（所属は重心で決める） | マスごとにキャンバスを分けると **境界で線が切れる**（隣のキャンバスは入力を受け取れない）。1 枚のキャンバスに合成する変種なら切れないが、結局「どの線がどのマスか」を自前で持つので案 A と同じになる |
| 消しゴム・投げなわ | 1 枚なので境界を意識しなくてよい | マスをまたぐ操作を自前で分配する必要がある |
| 性能 | 1 枚の PKDrawing に数千本。PencilKit の得意分野（メモアプリは数万本を扱う） | 月 43 枚、年 372 枚のキャンバスは重すぎる |
| 元に戻す | ひとつの履歴 | マスごとに分かれて操作感が崩れる |
| 保存 | 線ごとに「所属マス＋マス相対座標」を持つ自前形式（§3.9） | マスごとに `PKDrawing` の `dataRepresentation()` をそのまま保存できる（楽） |
| 同期の衝突解決 | 線単位（Web 版と同じ） | マス単位になり、同じマスを二つの端末で書くと片方が消える |

**決定: 案 A。** 「紙全体で 1 枚の `PKCanvasView`、線（`PKStroke`）ごとに自前の id と所属マスを持ち、保存はマス相対座標。レイアウトが変わるたびに各線を平行移動して 1 枚の `PKDrawing` に合成し直す」。
案 B の長所（保存が楽）は、§3.9 の自前形式で十分に補えます。

### 3.4 線の id と所属マス

`PKStroke` には id がありません。そこで次の二層で管理します。

```
  自前の台帳（InkPage）                       画面（PKCanvasView.drawing）
  ┌────────────────────────────────┐          ┌─────────────────────────┐
  │ id: "8f3c…"                    │ 合成 →   │ PKStroke                │
  │ cell: "2026-10-04"（所属マス）   │          │   path: マス相対の点列    │
  │ tool/color/width               │          │   transform: マスの左上へ │
  │ pts: マス相対の点列（§3.9）       │ ← 差分   │     平行移動（毎回計算）   │
  │ t: 書いた時刻                   │          └─────────────────────────┘
  └────────────────────────────────┘
       指紋 → id の対応表（メモリ内）
       指紋 = (path.creationDate, 点の数, インクの種類, 最初の点の位置)
```

- **表示**: 台帳の各線を `PKStroke(ink:, path:, transform: マス左上への平行移動)` にして `PKDrawing(strokes:)` を作り、`canvasView.drawing` に入れます。`path`（点列）はマス相対のまま、置き場所は `transform` だけで決めます。
- **新しい線**: `canvasViewDrawingDidChange` が呼ばれたら、キャンバスの線を一本ずつ「指紋」で引き、台帳に無いものが **新しい線** です。
  - 指紋 = `path.creationDate`（線を書き始めた時刻、マイクロ秒精度）＋点の数＋インクの種類＋最初の点の位置。`transform` に依存しないので、合成し直しても変わりません。
  - 新しい線は UUID を付け、所属マスを決め（下記）、点列をマス相対（紙座標 − マスの左上）に直して台帳へ。
- **消えた線**: 台帳にあってキャンバスに無い線 = 消しゴムで消された線。墓標（id と時刻）を残します（§5.3）。
- **所属マスの決め方**: 線の **外接矩形の中心**（`renderBounds` の中心）が入っているマス。Web 版の移行処理と同じ規則です。
  - 月ページの横方向: 列の幅は固定なので、隣の日にはみ出した部分もずれません（行は上下にしか動かない）。
  - 行をまたぐ線（上下）: 中心のある行と一緒に動く。隣の行の予定の数が変わると、はみ出した部分が隣の行の内容と少しずれます。これは **紙の仕様として受け入れます**（線を切らない方が大事。Web 版の移行でも同じ規則）。
  - 週ページ: 終日帯の 7 マス（`allday:2026-10-04` など）と時間軸全体（`grid`）。時間軸の中の線は列をまたいでも同じ領域なので、ずれません。
  - 日ページ: 終日帯（`allday`）と、時間軸＋右のメモ欄をまとめた領域（`grid`）。
  - 年ページ: `MM-DD`（存在しない 2/30 にも書ける）。左の日付帯は 1 月の列に属する（x が負になる）。
  - 月ページのメモ欄: `memo`。
- **マスの鍵（CellKey）は日付で持ちます**（行番号・列番号ではなく）。将来「後ろの週を隠す」などの変更をしても手書きが迷子になりません。

### 3.5 レイアウトが変わったときの合成し直し

レイアウトが変わる場面: 予定が読み込まれた・増えた・減った、月をまたいだ、手書きが行の下端を超えた、向きが変わった（倍率だけなので合成は不要）。

```
  予定の変化 ─┐
  手書きの増加 ┼→ Layout モジュールが各マスの矩形を計算
  ページ切替 ─┘        │
                       ▼
          台帳の各線に新しい transform を付けて PKDrawing を作り直す
                       │
                       ▼ （ペンを離している時だけ。書いている最中は保留）
          canvasView.drawing = 新しい PKDrawing
          contentSize を更新。画面上の位置が動かないようスクロール位置を補正
```

- **ペンが触れている間は絶対に `drawing` を入れ替えない**（線が消えたり、紙が動いたりします）。`canvasViewDidBeginUsingTool` / `canvasViewDidEndUsingTool` で状態を持ち、保留した更新はペンを離した 300 ms 後にまとめて反映します。
- 合成し直しは線の数に比例する処理（`transform` を付け替えるだけ）。5,000 本で数十 ms。
- スクロール位置の補正: 今見えている先頭の行を基準に、その行より上の高さの増減分だけ `contentOffset` をずらす（Web 版の `keepPageInPlace` と同じ考え）。

### 3.6 道具

**決定: ツールバーは自前（SwiftUI）。iPad 標準のツールパレット `PKToolPicker` は使わない。** 理由:

1. `PKToolPicker` の投げなわで選んだ線を **アプリから読む公開 API がありません**。「投げなわで囲んで予定にする」が作れません。
2. 「予定」ツールのような独自の道具を足せません。
3. 定規・ピクセル消しゴムなど、「線を線ごと扱う」前提（§3.4）を壊す道具が入っています。

道具ごとの実装:

| 道具 | 実装 |
| --- | --- |
| ペン | `canvasView.tool = PKInkingTool(.pen, color:, width:)`。太さ 細 2 / 中 3.5 / 太 6（lu、Web 版と同じ数字） |
| マーカー | `PKInkingTool(.marker, color:, width: 18)` |
| 消しゴム | `PKEraserTool(.vector)` = **線ごと消す**。半径は OS 既定（iOS 16.4 以降は `width:` 指定可。Web 版の 10 lu 相当にする） |
| 投げなわ | **自前**。キャンバスの上に透明な入力ビューを重ね（この道具の時だけ有効）、Pencil で描いた閉じた多角形の中に **点の 50% 以上** が入る線を選ぶ（Web 版 `strokeInLasso` と同じ）。点は `path.interpolatedPoints(by: .distance(4))` を使う。選択は破線の枠＋「予定にする／削除／選択解除」のメニュー。枠の中をペンでドラッグすると移動（離したときに「元の線を削除＋移動した複製を追加」の 1 操作にする。複製は **新しい id**。Web 版と同じで、同期の和集合がきれいに働く） |
| 予定 | **自前**。同じ入力ビューで矩形ドラッグ → 15 分丸め → 予定の作成画面。タップは既存の予定の編集（§4.5） |

投げなわ・予定ツールの間は `canvasView.drawingGestureRecognizer.isEnabled = false`（Pencil が線を描かないように）。指のスクロールはそのまま効きます。

### 3.7 消しゴム・投げなわがマスをまたぐ場合

- 消しゴム: PencilKit が線ごと消すだけなので、マスは関係ありません。消えた線は §3.4 の差分で分かります。
- 投げなわ: 複数のマスの線がまとめて選ばれてよい。「予定にする」のときの日時は、**選択範囲の外接矩形の中心**が入っているマス（と、週・日なら y から求めた時刻）で決めます（Web 版 `rectToEventRange` と同じ）。
- 移動: 複製の所属マスは移動後の中心で決め直します（別の日に書き直したことになる）。
- 行をまたいで動かした結果、線の中心が「存在しない日」の斜線マス（年ページ）に入ってもそのまま置けます（紙だから）。
- **紙の外（中央寄せの余白）に書いた線は保存しない**（M4c、M4C-25）: 外接矩形の中心が紙の外にある線は台帳に入れず、キャンバスからも消す（元に戻すにも残らない）。`inkCell(forCenter:)` が紙の外を端のマスに負の相対座標で保存してしまい、別の倍率や Web 版で紙の外に線が出るため。

### 3.8 ズーム・スクロール・向きの変更

- ピンチ拡大は `PKCanvasView` 自身の `minimumZoomScale`（幅ぴったり）〜 `maximumZoomScale`（その 4 倍）。線の太さは紙の座標で決まるので、拡大しても手書きと罫線の関係は変わりません。（M4c: 最小 = 一覧 fitAll、最大 = max(4 × 幅ぴったり, 2 × 読める倍率)（§2.2）。`PKCanvasView` の delegate を自前の Coordinator にすると `UIScrollView` はズーム対象を `viewForZooming(in:)` に問い合わせるので、Coordinator が PKCanvasView の描画サブビューを返す（F4、[M4C_CONTRACT.md §2.5](M4C_CONTRACT.md)）。ピンチ中・跳ね返り中は紙の窓を作り直さず引き伸ばし、終わりに 1 回描き直す（F3）。投げなわ／予定ツールの指の入力は overlay の hitTest でなく容器の認識器で受け、2 本目の指でピンチに譲る（F2））
- 向きを変えたら「幅ぴったり」の倍率を計算し直し、画面中央にあった紙の点が中央に残るように `contentOffset` を補正。`drawing` の入れ替えは不要（マスの矩形は lu で不変）。（M4c: 一覧で見ていれば新しい一覧へ、拡大中は絶対倍率を保って新しい範囲に clamp。clamp で削られた分は目標倍率として持ち、戻したとき復元。保存比率は回転では書き換えない。M4C-24）
- 指 2 本の操作（ピンチ）と Pencil の線は同時に起きない（Pencil が触れている間はピンチを無視）。
- スクロール中に Pencil が触れたらスクロールを止めて線を描く（PencilKit の既定動作）。

### 3.9 保存形式とバージョン

**決定: 自前の JSON 形式で、1 本の線を「PencilKit の制御点をすべて含む点列」として保存する。** `PKDrawing.dataRepresentation()` は使いません。

| 観点 | `dataRepresentation()`（PencilKit の独自形式） | 自前 JSON（決定） |
| --- | --- | --- |
| 中身 | 非公開のバイナリ。線ごとに分解できない。新しい OS で書いたものを古い OS が読めないことがある（`PKContentVersion` で制限は可能） | 線ごとに id・所属マス・点列。読める・差分が取れる・Web 版と同じ構造 |
| 同期の衝突解決 | 線単位にできない | 和集合＋墓標がそのまま使える |
| 将来の乗り換え・書き出し | PencilKit 依存 | 誰でも読める |
| 再現性 | 完全 | `PKStrokePath(controlPoints:creationDate:)` に同じ制御点を渡せば **同じ線** になる（点列が B スプラインの制御点そのもの） |

形式（`InkPage`、Web 版の `PageDoc` と同じ骨組み）:

```json
{ "v": 1,
  "pageId": "m1-2026-10",
  "strokes": {
    "8f3c…": { "id": "8f3c…", "cell": "2026-10-04", "tool": "pen", "color": "#1f2937",
               "t": 1760150400123, "dev": "iPad-…",
               "pts": [ x, y, dtMs, sizeW, sizeH, opacity, force, azimuth, altitude,  …9 個ずつ ] }
  },
  "deleted": { "a1b2…": 1760150500000 },
  "updatedAt": 1760150500000 }
```

- `pts` は 1 点につき 9 個（位置 x,y はマス相対 lu を 0.1 丸め、時刻差は ms 整数、太さ・不透明度・筆圧は 0.01 丸め、方位・傾きは 0.001 rad 丸め）。`PKStrokePoint` の全属性です（iOS 17 の `secondaryScale` は使うインクに無関係なので保存しない。将来必要なら 10 個目として追加）。
- `pageId` は Web 版と同じ文字列（`d-2026-10-04` / `w-2026-09-28`（月曜）/ `m1-2026-10` / `y-2026`）。
- **バージョン**: `v` を見る。読み手が知らない `v` や項目は **捨てずにそのまま保持**して書き戻す（同期で古い端末が新しい端末のデータを消さないため）。`tool` が未知の線は表示だけ飛ばして保持。
- 圧縮: 保存・送信時に LZFSE（`Compression` フレームワーク）。目安は §5.6。
- インクの種類は初版では `pen` と `marker` のみ。`PKCanvasView.maximumSupportedContentVersion = .version1` にして、OS が新しいインクを勝手に使わないようにします。

**書き出しファイル `tegaki-app-export` v1**（M6 で実装。[M6_CONTRACT.md](M6_CONTRACT.md) §1.1、`TegakiKit/Sources/InkModel/AppExport.swift`。設定 › データ › 「手書きを書き出す」›「データファイル（JSON、すべてのページ）」が作るファイル。[SUPPORT.md](SUPPORT.md) の FAQ「手書きを書き出すには？」の「形式は開発者向けに設計書と README に載せています」の受け皿）。鍵はソート順、2 スペース字下げの整形 JSON で、実際のファイルはこの形:

```json
{
  "app": "ios/1.0 (12)",
  "exportedAt": "2026-10-17T21:03:00+09:00",
  "format": "tegaki-app-export",
  "pages": [
    {
      "deleted": {
        "3f0c…": 1760000009000
      },
      "pageId": "m1-2026-10",
      "strokes": {
        "8f3c…": {
          "cell": "2026-10-14",
          "color": "#1f2937",
          "dev": "ipad-…",
          "id": "8f3c…",
          "pts": [24, 150, 0, 3.5, 3.5, 1, 0.5, 0, 1.4, 28.2, 154.3, 12, 3.5, 3.5, 1, 0.56, 0, 1.4],
          "t": 1760000000000,
          "tool": "pen"
        }
      },
      "updatedAt": 1760000000000,
      "v": 1
    }
  ],
  "v": 1
}
```

| 項目 | 型 | 規則 |
| --- | --- | --- |
| `format` | String | 必ず `"tegaki-app-export"`。違えば取り込み口は Web 版の形式（`tegaki-web-export`、§6）を試し、どちらでもなければ「このファイルは手書きの書き出し（Web 版またはこのアプリ）ではありません」 |
| `v` | Int | 1。2 以上は読まない（`unsupportedVersion`。Web 形式と同じ扱い） |
| `exportedAt` | String | ISO 8601、端末のローカル時刻＋オフセット、秒まで（`2026-10-17T21:03:00+09:00`）。表示用 |
| `app` | String | `"ios/<CFBundleShortVersionString> (<CFBundleVersion>)"`。表示用 |
| `pages` | [Object] | 各要素は上の保存形式（`InkPage.jsonValue`）そのもの: `v`・`pageId`・`strokes`（id → 線。墓標済みは書かない）・`deleted`（id → ms）・`updatedAt`・未知の鍵の書き戻し。週・日の帯の線の移し替え（`BandMigration`）を通した後の形。順序は `pageId` の昇順。空ページ（線も墓標も未知の線も無い）は入れない。墓標だけのページは入れる（復元で「消した線」を消したままにするため） |
| `pages[].strokes[id]` | Object | `{ id, cell, tool("pen"\|"marker"), color "#rrggbb", t, dev?, pts: [9 数 × 点] }`（点は x, y, dtMs, sizeW, sizeH, opacity, force, azimuth, altitude。上の表の丸めのまま） |

- 整形の規則（`JSONValue.serialized(pretty: true)`）: object は 1 鍵 1 行（鍵はソート、2 スペース字下げ、空は `{}`）、数値だけの配列（`pts`）は 1 行、それ以外の配列は 1 要素 1 行（空は `[]`）。端末のファイルと iCloud の圧縮形（`serialized()`、`InkPageCodec`）は M6 でも不変。
- 往復は無損失: `pages[i]` を `InkPage(json:)` で読むと元のページと `==`（点ごとの太さ・不透明度・筆圧・方位・傾き、`cell`、`dev`、墓標、未知の鍵が全部戻る）。Web 版の形式を採らなかったのはこれが成り立たないから（点の属性と `cell` が落ち、伸びた行の線が別のマスに落ちる。M6_CONTRACT D1）。
- 取り込み（復元）は 設定 › データ › 「Web 版の手書きを取り込む」（購読中）。`InkImport.parse` がトップレベルの `pages` 配列をページ単位のバイト範囲に切り分けて 1 枚ずつ解析し（JSON の木を一度に持たない。ファイルの目安はおおむね 200 MB まで）、`SyncEngine.importPages` が `InkPage.merge` で合流する: 同じファイルを二度取り込んでも二重にならず、書き出した後にアプリで消した線は戻らない（墓標が勝つ。全部を元に戻すときは「この iPad の手書きを全て消す」の後に取り込む）。
- `dev` は書いた端末の印（`identifierForVendor`。このアプリ用のランダムな識別子で、端末名やシリアル番号ではない）。書き出しでも落とさない（往復の `==` と、同じ id の線が食い違ったときの決定的な選び方 `InkPage.compareStrokes` が使うため）。共有先に渡ることは [PRIVACY.md](PRIVACY.md) §4 に書いてある。

### 3.10 性能とメモリ

| 場面 | 方針 |
| --- | --- |
| 1 ページに数千本 | 1 枚の `PKDrawing`。PencilKit の描画は問題なし。自前の処理（差分・合成・投げなわ判定）はすべて線の数に比例する単純なもの |
| 差分の検出 | 指紋 → id の辞書（メモリ内）。線 1 本につき定数時間 |
| 投げなわの判定 | 外接矩形で先に絞ってから点の内外判定（Web 版と同じ） |
| ページ切替 | キャンバスは **1 枚を使い回し**、`drawing` だけ差し替える。台帳はメモリに **今のページ＋前後 1 ページ**（先読み）。それ以外は捨てる（端末内ファイルから数十 ms で読める） |
| スワイプの動き | 出ていくページのスナップショット画像を横に滑らせ、裏で次のページを用意 |
| 1 枚のキャンバスの大きさ | 年ページは 1400 × 最大 31 × 400 lu。PencilKit は描画をタイル管理するので実用上問題なし。上限（§2.2）で頭打ち |
| 起動 | 最後に見ていたページの台帳を読む → 表示 → その後で iCloud を見に行く（§5） |

### 3.11 Apple Pencil の機能

`UIPencilInteraction` をキャンバスに付け、**iPad の設定（設定 › Apple Pencil）で本人が選んだ動作を尊重**します。

| 設定の値（`UIPencilInteraction.preferredTapAction` / `preferredSqueezeAction`） | アプリの動き |
| --- | --- |
| `.switchEraser`（既定） | ペン/マーカー ⇄ 消しゴム。1 秒だけ「消しゴム」「ペン」のトースト |
| `.switchPrevious` | ひとつ前の道具に戻る |
| `.showColorPalette` / `.showInkAttributes` | ペン先の近く（ホバー位置、無ければツールバー）に色と太さのポップオーバー |
| `.showContextualPalette`（スクイーズの既定、17.5〜） | 同上（道具＋色の小さなパレット） |
| `.ignore` / `.runSystemShortcut` | 何もしない（OS に任せる） |

- 実装: iPadOS 17.5 以降は `pencilInteraction(_:didReceiveTap:)` と `pencilInteraction(_:didReceiveSqueeze:)`（スクイーズは `phase == .ended` で 1 回）、17.0〜17.4 は従来の `pencilInteractionDidTap(_:)`。`#available` で分けます。
- ホバー（対応機種のみ）: `PKCanvasView` が **自動で** ペン先の着地位置と太さをプレビューします。追加実装なし。
- バレルロールは使いません。
- **2 本指タップは実装しません**（Web 版はダブルタップが届かないための代替でした）。ただし Apple Pencil 第 1 世代・USB-C 版にはダブルタップが無いので、要望があれば「設定で 2 本指タップをオンにできる」形で後から足せる設計にしておきます（ジェスチャー認識は Web 版 `gestures.js` の規則をそのまま移せます）。

### 3.12 Scribble の抑制と指の扱い

- 紙の上（キャンバスの中や近く）には **テキスト入力欄を置きません**。Scribble（手書き→文字）が Pencil の線を横取りするからです。
- 予定の作成・編集はモーダルのシート（紙を覆う）の中で行い、タイトル欄は普通の `TextField`。ここでは Scribble が **働いてほしい** ので抑制しません（「ここにペンで書くと文字になります」のプレースホルダー）。
- 将来、紙の横に入力欄を置くことになったら `UIScribbleInteraction` の `scribbleInteraction(_:shouldBeginAt:)` で抑制します。
- 指: `drawingPolicy = .pencilOnly` の間、指はスクロール・ピンチ・タップだけ。手のひらが触れても線は引かれません。

### 3.13 元に戻す／やり直す

- **自前の履歴**（Web 版の `Op`: add / remove / batch と同じ）。`PKCanvasView` の `undoManager` は使いません。理由: `drawing` を合成し直すたびに PencilKit の履歴が壊れる、投げなわ移動や「予定にして消す」が PencilKit の外で起きる。
- 3 本指スワイプ（OS の取り消しジェスチャー）が PencilKit の履歴に届いて線が消えることがあります。その場合も §3.4 の差分で「消えた線」として台帳に反映されるので、台帳と画面は食い違いません。消えた線が再び現れたら（OS のやり直し）、墓標のある id は復活させず **新しい id の複製** として扱います。

## 4. 予定（EventKit）

### 4.1 許可を求めるタイミングと文言

- タイミング: 初回案内の 3 枚目（§2.10）で説明してから、本人がボタンを押したときに `EKEventStore.requestFullAccessToEvents()`。起動直後にいきなり出しません。
- 状態は `EKEventStore.authorizationStatus(for: .event)`。`.fullAccess` 以外（`.denied` `.restricted` `.writeOnly`）なら、紙は手書き専用で使え、ヘッダーに「予定を表示するには設定でカレンダーを許可」のバナー（「設定を開く」で `UIApplication.openSettingsURLString`）。
- Info.plist の目的文（`NSCalendarsFullAccessUsageDescription`）:
  「カレンダーの予定を手帳のページに表示し、手書きから予定を作るために使います。iPadOS には読み取りだけの許可が無いため、フルアクセスをお願いしています。予定は iPad の中だけで扱い、外部には送りません。」
- 書き込み専用の許可（`.writeOnly`）は求めません（表示ができないので意味がない）。

### 4.2 変更の購読

- `NotificationCenter` の `.EKEventStoreChanged` を購読。届いたら、今見ている範囲の予定を取り直す（1 秒のデバウンス）→ 行の高さを計算し直す → 手書きを合成し直す（ペンを離している時だけ、§3.5）。
- 加えて、前面に戻ったとき・ページを変えたとき・5 分ごとにも取り直し（iOS が Google から取得するのは別のタイミングなので、こちらは軽い処理）。

### 4.3 カレンダーの選択

- `eventStore.calendars(for: .event)` をアカウント（`EKSource`）ごとにまとめて設定画面に一覧。Google は `source.sourceType == .calDAV`（表示名は iPad の設定で付けた名前。「Gmail」「Google」など）。
- 初期値: すべて表示。ただし **祝日カレンダー**（タイトルに「祝日」「Holidays」を含む購読カレンダー、`type == .subscription`）と **誕生日**（`.birthday`）は初期値で非表示。祝日は §4.8 の自前計算で出すので二重になるからです。
- 予定の登録先: 初期値は `eventStore.defaultCalendarForNewEvents`。設定で `allowsContentModifications == true` のカレンダーから選べる。
- 色: `calendar.cgColor`。Google の「予定ごとの色」は iPad に同期されないので、常にカレンダーの色です（§4.7）。

### 4.4 表示するもの

| 種類 | 扱い |
| --- | --- |
| 終日（`isAllDay`） | 月・週の終日帯・年にチップ。複数日は帯。EventKit の終日の `endDate` は **最終日の 23:59:59** なので、内部では Web 版と同じ「翌日 0:00（排他）」に直して扱う |
| 時間指定 | 週・日の時間軸に箱（重なりは列分割、Web 版 `layoutTimedEvents` を移植）。月は「9:00 会議」のチップ |
| 24 時間以上の時間指定 | 終日帯には入れず、またがる各日の時間軸に切って描く（Web 版と同じ） |
| 繰り返し | `events(matching:)` が回ごとに展開して返すので、そのまま表示。編集・削除で「この回だけ／以降すべて」を聞く（§4.6） |
| 辞退した招待 | 非表示 |
| 取得範囲 | 表示ページの範囲＋前後 1 ページ分。`predicateForEvents(withStart:end:calendars:)` は 4 年までなので年ページも 1 回で済む |

### 4.5 予定の作成

| 入口 | 動き |
| --- | --- |
| 予定ツールでなぞる（週・日） | 列から日付、y から 15 分丸めの開始・終了。30 分未満は 1 時間に。プレビューの矩形を表示して離したら作成シート |
| 予定ツールでタップ（月・年） | そのマスの日の終日予定。月のメモ欄なら「今日が今月なら今日、違えば 1 日」（Web 版と同じ） |
| 投げなわ →「予定にする」 | 選択範囲の中心から日時を決め、手書きの画像をシートの上に表示（参考用）。保存後に「この手書きを消す」（既定オン）なら線を削除（元に戻せる） |
| ＋予定ボタン | 今日 9:00〜10:00（月・年のページでは今日の終日） |

作成シート: タイトル（Scribble で書ける）、終日スイッチ、日付／開始・終了、カレンダー、場所、メモ。保存で `EKEvent` を作り `eventStore.save(event, span: .thisEvent, commit: true)`。終日は `isAllDay = true`、開始 = 初日 0:00、終了 = 最終日 0:00（EventKit が最終日いっぱいに正規化。M2 で実機確認）。

### 4.6 編集・削除

- 指で帯・チップ・箱をタップ → 編集シート。`calendar.allowsContentModifications == false` なら読み取り専用（閉じるのみ）。
- 繰り返しの予定（`hasRecurrenceRules` または `isDetached`）: 保存・削除の前に「この回だけ」「以降すべて」を選ぶ → `span: .thisEvent` / `.futureEvents`。Web 版では「この回だけ」しかできなかったので、アプリ版の方が多機能です。
- 削除は確認ダイアログのあと `eventStore.remove(event, span:, commit: true)`。
- 予定の識別: `calendarItemIdentifier` ＋ `occurrenceDate`（回ごと）。`eventIdentifier` は同期で変わることがあるので使いません。

### 4.7 Google 固有の制約（本人・利用者への説明にも使う）

| 制約 | 説明 |
| --- | --- |
| 予定ごとの色が無い | Google の「この予定だけ赤」は iPad に同期されない。カレンダーの色で表示 |
| 反映の速さ | iPad が Google から取得する間隔は iPad の設定「データの取得方法」次第（プッシュ非対応。「自動」だと充電中＋Wi-Fi のときだけ）。初回案内で「15 分ごと」を勧める。アプリから書いた予定は iPad のカレンダーには即時、Google には次回の同期で届く |
| できないこと | Google カレンダーの新規作成、ゲストへのメール通知、Google タスク、拡張プロパティ（Web 版が付けていた「tegaki」の印） |

### 4.8 祝日（自前計算）

## 5. 同期（CloudKit プライベートデータベース）

### 5.1 全体像

```
  iPad A                          iCloud（本人のアカウント）              iPhone / iPad B
  ┌──────────────┐                ┌──────────────────────┐             ┌──────────────┐
  │ 端末内ファイル │ ─ 保存 1.5 秒後 ─▶│ 専用ゾーン "tegaki"     │ ◀─ 変更通知 ─ │ 端末内ファイル │
  │ (InkPage)    │ ◀─ 変更を取得 ── │   レコード = 1 ページ    │ ─ 変更を取得 ▶│              │
  └──────────────┘                │   本文は CKAsset(圧縮)   │             └──────────────┘
                                  └──────────────────────┘
```

- 開発者はこのデータを **見られません**（プライベート DB は開発者ポータルからも見えない）。容量は本人の iCloud に数えられます。
- 端末内ファイルが常に主。iCloud は「ほかの端末へ届ける経路」と「バックアップ」です。オフラインでも全部使えます。

### 5.2 レコード設計

**決定: 1 ページ = 1 レコード**（Web 版の「1 ページ × 1 端末 = 1 ファイル」とは違います。理由: CloudKit には「サーバー側が変わっていなければ保存」という仕組み（`savePolicy = .ifServerRecordUnchanged`）があり、Drive に無かった衝突検出ができるから。レコード数も端末数倍にならない）。

| 項目 | 値 |
| --- | --- |
| コンテナ | `iCloud.com.syfan0.tegakicalendar`（仮。バンドル ID と対にする） |
| データベース | プライベート |
| ゾーン | 専用ゾーン `tegaki`（変更トークンで差分取得できる。既定ゾーンでは不可） |
| レコード種別 | `InkPage` |
| recordName | `pageId`（`m1-2026-10` など）。そのまま鍵になる |
| フィールド | `schema: Int`（= `v`）、`updatedAt: Date`、`strokeCount: Int`、`doc: CKAsset`（LZFSE 圧縮した InkPage JSON）、`app: String`（書いたアプリとバージョン） |
| サイズ | レコード本体の上限 1 MB を避けるため、本文は **常に CKAsset**（小さくても） |
| 設定の同期 | 表示するカレンダーなどは端末ごと（同期しない）。ただし「Web 版から取り込み済み」「購読の試用開始」の印は `Meta` レコード 1 件に持つ |

### 5.3 衝突解決（和集合＋墓標）

Web 版 `mergePages` と同じ規則を `InkModel` に移植します。線には自前の id があるので（§3.4）、PencilKit でもそのまま成り立ちます。

```
  merge(a, b):
    strokes = a.strokes ∪ b.strokes        （同じ id は同じ線。内容は変わらない前提）
    deleted = a.deleted ∪ b.deleted        （同じ id は時刻の大きい方）
    strokes から deleted にある id を除く
    updatedAt = max
```

- 投げなわで動かした線は「元を削除＋新 id で追加」なので、別の端末で元を消していても矛盾しません。
- 保存の流れ: 端末内に書く → 1.5 秒待つ（続けて書く間はまとめる）→ 端末内の最新を iCloud のレコードへ `.ifServerRecordUnchanged` で保存 → `serverRecordChanged` が返ったら **サーバー版と merge して再保存**（最大 3 回。それでも駄目なら次回）。
- 取得の流れ: 起動時・前面復帰時・サイレント通知時に `CKFetchRecordZoneChangesOperation`（前回の変更トークンから差分）→ 各ページを端末内と merge → 今見ているページなら画面に反映（履歴は保つ）。
- ページを開いた直後にも、そのページだけ `CKFetchRecordsOperation` で最新を取りに行く（他端末で書いた直後に開く場面のため）。
- 通知: `CKRecordZoneSubscription` ＋ サイレントプッシュ（Background Modes: remote-notification）。届かなくても次の前面復帰で追いつく。

### 5.4 オフラインと iCloud 未サインイン

| 状態 | 動き |
| --- | --- |
| オフライン | 端末内に保存、`dirty` 一覧に積む。ヘッダー「オフライン」。回線が戻ったら送る（15 秒から 5 分まで倍々で再試行） |
| iCloud 未サインイン（`accountStatus != .available`） | 全機能が端末内だけで動く。ヘッダー「この iPad のみ」。設定画面に「iCloud にサインインするとほかの端末と同期できます」 |
| iCloud 容量不足（`quotaExceeded`） | 端末内には保存し続ける。ヘッダー「エラー」＋設定に理由 |
| アカウントの切り替え（`.CKAccountChanged`） | 端末内データは最初に同期したアカウントの `userRecordID` に紐付けて記録。別アカウントになったら **同期を止めて** 「このiPadの手書きは別の iCloud のものです。新しいアカウントで使い始めますか（手書きは残ります／消します）」を聞く。黙って混ぜない |
| 再インストール | 端末内は消えるが iCloud から全ページを取り直す（起動時の差分取得が全件になる） |

### 5.5 端末内キャッシュ

- 置き場所: `Application Support/Ink/<pageId>.json.lzfse`（iCloud Drive の対象外。iTunes バックアップには含まれる）。
- 状態ファイル: `Ink/state.json` = `{ dirty: [pageId], zoneToken: Data, account: String, seen: { pageId: recordChangeTag } }`。
- 書き込みは一時ファイルに書いてから置き換え（途中で落ちても壊れない）。
- 「この iPad の手書きを全て消す」= 端末内を消し、iCloud のレコードも全て削除（確認 2 回。利用規約第 4 条・プライバシーポリシー第 9 条の「データの削除」に対応）。

### 5.6 容量の目安

| 単位 | 目安 |
| --- | --- |
| 線 1 本 | 制御点 30〜60 個 × 9 値 ≈ 2〜3 KB（JSON）→ 圧縮後 0.6〜1 KB |
| 1 ページ（よく書く月、500 本） | 約 0.4 MB（圧縮後） |
| 1 年分（日 365＋週 53＋月 12＋年 1、合計 2〜4 万本） | 15〜40 MB |
| iCloud の無料枠 5 GB | 100 年分でも余る。写真と共用なので「使っていることは設定画面に表示」 |

墓標は小さいので永久に残します（1 年を超えた墓標を掃除する処理は将来の課題として明記）。

## 6. Web 版からの移行

### 6.1 Web 版に足すもの: 「書き出し」

設定画面に「手書きを書き出す（iPad アプリ用）」を追加します（Web 版リポジトリの作業。別タスク）。

1. Drive 上の **全端末分の全ページ** を集める（`appDataFolder` の全ファイルを一覧 → ページごとに `mergePages`）。お試しモードの手書きは別 DB なので、「お試しの手書きも含める」のチェックを付ける。
2. 次の JSON を作り、ファイルとして保存（iPad の Safari なら「ファイル」アプリのダウンロードに入る）。

```json
{ "format": "tegaki-web-export", "v": 1, "exportedAt": "2026-10-11T12:00:00+09:00",
  "pages": [ { "v": 1, "pageId": "m1-2026-10", "strokes": { "…": { "id": "…", "tool": "pen", "color": "#1f2937", "size": 3.5,
                 "pts": [x, y, p, …], "t": 1760000000000 } }, "deleted": {}, "updatedAt": 1760000000000 } ] }
```

（`pages` の中身は Web 版の `PageDoc` そのもの。生きている線だけで、墓標は空でよい。）

### 6.2 iPad アプリ側: 「取り込む」

設定 › データ › 「Web 版の手書きを取り込む」→ ファイル選択（`UIDocumentPickerViewController`、JSON）→ 変換 → 各ページに **追加**（既存の線は消さない）→ iCloud へ。

- 線の id は Web 版のものをそのまま使う（UUID でなくても文字列なら可）。**同じファイルを二度取り込んでも二重にならない**（同じ id は同じ線）。
- 進捗バーと「取り込んだページ数・線の数」を表示。完了の印を `Meta` レコードに記録（再度の取り込みは可能）。

### 6.3 座標の変換（Web の紙座標 → マス相対座標）

Web 版の紙の幅とアプリ版の紙の幅は同じ（§2.2）なので、**平行移動だけ**です。所属マスは線の外接矩形の中心 (cx, cy) で決めます。

| ページ | Web の座標系 | マスの決め方 | 相対座標 |
| --- | --- | --- | --- |
| 月 `m1-YYYY-MM` | 1400 × 1750。グリッドは y < 1050、マス 200 × 175（行 r = floor(cy/175)、列 c = floor(cx/200)）。y ≥ 1050 はメモ欄 | グリッドの 42 日のうち (r, c) の日付 → `YYYY-MM-DD`。cy ≥ 1050 → `memo` | 日付マス: (x − 200c, y − 175r)。メモ: (x, y − 1050) |
| 週 `w-YYYY-MM-DD` | 1400 × 1920。左帯 64、列幅 190.857、1 時間 80 | 全て `grid`（Web の週ページには紙の上に終日帯が無い） | (x, y) そのまま |
| 日 `d-YYYY-MM-DD` | 1000 × 2400。左帯 72、時間軸 72〜660、メモ 660〜1000、1 時間 100 | 全て `grid` | (x, y) そのまま |
| 年 `y-YYYY` | 1400 × 1860。左帯 56、列幅 112、行高 60 | 月 m = floor((cx − 56)/112)（cx < 56 なら 0）、日 d = floor(cy/60) + 1 → `MM-DD` | (x − 56 − 112m, y − 60(d − 1)) |

- 2026 年より前の「日曜始まり」のページ（`w-<日曜>`、`m-YYYY-MM`）は Web 版 1.0.4 で月曜ページに写し済みなので、書き出しには **月曜ページだけ** を含めます。
- 日付が未来にずれないよう、変換は純粋関数（`InkModel/WebImport.swift`）にして、Web 版のテストデータと同じ入力で XCTest を書きます。

### 6.4 線の属性の変換

| Web | PencilKit |
| --- | --- |
| `tool: pen`, `color`, `size`（細 2 / 中 3.5 / 太 6） | `PKInk(.pen, color)`。各点の太さ = size × (0.4 + 0.9 × p)（Web の式。見た目をなるべく揃える） |
| `tool: highlighter`, `color`（4 色）, 幅 18 | `PKInk(.marker, color)`。各点の太さ 18 |
| `pts: [x, y, p, …]`（筆圧 p 0〜1） | `force = p`、`opacity = 1`（マーカーは 0.35 相当を色の α で）、`azimuth = 0`、`altitude = π/2`、`timeOffset = 8 ms × 番号` |
| `t`（作成時刻） | `PKStrokePath.creationDate` と台帳の `t` |

Web の点列は制御点ではなく「ならした通過点」なので、PencilKit のスプラインはわずかに内側を通ります（画面上で 1 px 未満）。許容します。

### 7.2 実装（M5 で確定。[M5_CONTRACT.md](M5_CONTRACT.md) §1〜§2、D1・D2・0-4）

- **StoreKit 2 だけ**: `Product.products(for:)` で商品を取り、`product.purchase()`。結果の `Transaction` は `finish()`。未完了の Transaction は起動時に `Transaction.unfinished` を 1 回走査して `finish()`。

- **StoreKit 層**（`Sources/TegakiCalendar/Store/`）は `Transaction` と `Status` をその入力に写すだけ（`StoreClient` プロトコル、`LiveStoreClient`、テスト用の偽物）。UI は `@MainActor` の `StoreModel` 1 つの `snapshot`（権利・価格 `offers`・購入中・結果の文言・App Store に届いたか・最初の確認が済んだか）から読む。`refresh()` は起動・前面復帰・`Transaction.updates` の到着・購入後に走り、走行中に重なったら合流せず終了後にもう 1 回走る（M5-37）。`Product.products` は価格が無いか 1 時間以上たったときだけ（M5-38）。

- 管理: 「サブスクリプションの管理」→ SwiftUI の `.manageSubscriptionsSheet(isPresented:)`（M5-21）。
- 試用の資格: `product.subscription?.isEligibleForIntroOffer` が false の人（以前試した人）には「無料試用の対象外です（お試しは 1 つの Apple Account につき 1 回）。」と価格だけ、CTA は「購入する」、説明文は「料金は購入の確認時に請求されます」（M5-17）。

### 8.2 モジュール分割

```
  TegakiCalendar.xcodeproj（XcodeGen）
   └─ App ターゲット（SwiftUI）
        └─ ローカル Swift パッケージ TegakiKit
             ├─ Layout     純粋: ページ幾何、行の高さ、マス矩形、矩形→日時、スクロール補正   （Foundation のみ）
             ├─ Holidays   純粋: 祝日計算                                                   （Foundation のみ）
             ├─ InkModel   純粋: InkPage、merge、id、JSON、圧縮、Web 取り込みの変換、投げなわの幾何（Foundation のみ）
             ├─ Ink        PencilKit: キャンバス制御、台帳⇄PKDrawing の変換、道具、Pencil 操作、履歴
             ├─ CalendarKit EventKit: 許可、取得、正規化（Web 版 CalEvent 相当）、作成・編集・削除
             ├─ Sync       CloudKit: レコード、ゾーン、差分取得、衝突解決の呼び出し、端末内キャッシュ、状態
             └─ Store      StoreKit 2: 商品、購入、権利、ペイウォール
   依存の向き: App → (Ink, CalendarKit, Sync, Store) → (Layout, InkModel, Holidays)
```

- **M1 の時点では**まだパッケージに分けていません。アプリターゲットの中のフォルダ（`Calendar/`・`Holidays/`・`Ink/`・`Views/`）で分けてあります。`DayKey`・`MonthLayout`・`JapaneseHolidays` は Foundation だけに依存させてあるので、M2 で TegakiKit に切り出すのはファイルの移動だけで済みます。
- **純粋なモジュール（Layout・Holidays・InkModel）は Foundation だけに依存**させます。すると **Xcode 無しのこの Mac でも `swift test` が通ります**（Command Line Tools の swift 6.4 で可）。開発の往復が CI 待ちにならない大きな利点です。
- Ink・CalendarKit・Sync・Store は iOS でしか動かないので、テストは CI のシミュレータで。

### 8.3 ビルドと配布（GitHub Actions）

| ワークフロー | 内容 |
| --- | --- |
| `build.yml`（push ごと。M1 で作成済み） | `macos-26` ランナー（Xcode 26.6）→ `brew install xcodegen` → `xcodegen generate` → `xcodebuild build -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO`（署名なし）→ iPad シミュレータ（無ければ iPhone）で `xcodebuild test`。TegakiKit を切り出したら `swift test` も足す |
| `testflight.yml`（手動実行。M2 で追加） | Secrets の証明書（.p12）とプロビジョニングプロファイルを一時キーチェーンへ → `xcodebuild archive` → `-exportArchive` → App Store Connect API キーで TestFlight へアップロード（`xcrun altool` または fastlane pilot） |

- 公開リポジトリなので macOS ランナーは無料。Secrets（証明書・API キー）は公開されません。
- 署名の素材は Web（Certificates, Identifiers & Profiles）＋ Keychain Access の CSR で作れ、Xcode は要りません。
- ローカルに Xcode を入れられた場合（ログインパスワードが通った場合）は、同じ `project.yml` を Xcode で開いて開発速度を上げます。CI の構成は変えません。

### 8.4 テスト方針

| 対象 | 方法 |
| --- | --- |
| Layout（行の高さ、マス矩形、矩形→日時、スクロール補正） | XCTest の純粋テスト。Web 版 `page-geometry` のテストを移植し、「予定が増えたら下の行だけ下がる」「手書きの下端で縮まない」を表で検証 |
| Holidays | 内閣府一覧 2000〜2027 と完全一致、国立天文台の春分・秋分 2020〜2050、2019〜2021 の特例、2006 以前の規則（M1 で移植・確認済み。§4.8） |
