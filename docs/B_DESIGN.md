## 0. 要約（本人向け）

**どうなるか**
- 日・週・月・年のページを、それぞれ横につなげます。指で横にすべらせると前後のページが続いて出てきて、**境目をまたいで、そのまま Apple Pencil で書けます**。iPhone（「指でも書く」がオン）では、横に動かすのは 2 本指です。
- 週は「日曜の右に次の週の月曜」、年は「12 月の右に次の年の 1 月」、日は「その日の右に次の日」。どれも日付の順に横へ続きます。
- 日と週の時刻は、今までどおり上から下です。だから夜中をまたぐ予定（例: 日曜の夜の夜行バスで、月曜の朝に着く）は、左の日の下の端から右の日の上へ、斜めに 1 本で書きます（今の週の中で、月曜の夜から火曜の朝へ書くのと同じ形です）。横にまっすぐ 1 本の帯になるのは、日のページの 24 時の下の「自由メモ」です。
- 月は、月のカレンダーを横に並べて貼ったように「10 月の表の右に 11 月の表」が並びます。表の右どなりは 4〜5 週あとの日なので、**表と表の間では日付は続きません**。月の表の上で日付どおりに続けて書けるのは、今と同じく 1 つの表の中（前後の月の薄い日まで）です。表と表の間をまたいで書けるのは、下の「メモ」欄です（横に 1 本の帯になります）。月末から月初へ日付どおりにまたぐ予定は、週のページで書きます。
- 一度に見える量: 縦向きでは、ほぼ 1 ページ（今と同じ大きさ）。横向きでは、11 インチで週が約 2.7 週、年が約 2.5 年、月が約 1.4 か月、日が約 4.7 日です。それ以上は縮められず、指ですべらせて続きを見ます（さらに縮めて何ページも見渡せるようにするかは、見本を見てから決めます。P-B10）。

**書いたものの保存**
- 保存と iCloud への送り方は、今までどおり 1 ページずつです。またいで書いた線は、線の真ん中があるページに 1 本のまま保存されます。新しい保存の形は作らないので、移し替えもありません。
- 古い版のままの端末では、またいだ線は片方のページにだけ出て、もう片方のページには出ません。iPhone では紙の端で切れて見えます。iPad では、紙の外の余白にはみ出して見えるかもしれません（どちらになるかは、見本の画面の画像で確かめてからお知らせします）。**消えたり壊れたりはしません。** ただし、古い版でその線を消すと、新しい版でも消えます。両方の端末を新しい版にしてから書くのが安心です。
- 線がとても多いと（特に年のページ）、重くならないように、隣のページが「見るだけ（書けない）」になったり、その種類だけ今の 1 ページずつに戻ったりすることがあります（1 回お知らせします。書いたものは消えません）。

**今と変わること**（→ の後は、いやなときの行き先）
1. iPad の一覧で、週・日・年の紙が指 1 本で横に動くようになります（今は動きません）。はじくと隣のページへめくれます。→ Apple Pencil で書いているときに手のひらで紙がずれないかは、試作版で確かめます。どうしてもいやなら設定でオフにできます（P-B7）。
2. 11 インチを横にした月の一覧では、左右に前後の月の表の端（1.5〜2 列ほどずつ）がいつも見えます。行の高さはそろっていません。→ 並べ方は見本の画像で選んでもらいます（P-B3）。
3. 月の最後の行がのびることがあります（隣の月とメモ欄の高さをそろえるため）。年の行は、前後の年のいちばん高い行にそろいます。週・日の終日予定の段が、隣の週の予定の分だけ増えることがあります。そのため、高さで大きさが決まる一覧（年、横向きの週など）は、今より少し小さくなることがあります。→ 見本の画像で確かめてもらいます。
4. 日の自由メモと月のメモの下に、隣のいちばん長い日・月の分だけ白紙が続きます。
5. iPhone を横にして一番縮めた状態は今のまま（24 時間全部が入る）で、左右に前後の日・週が小さく並びます。重すぎるときだけ大きさに上限を付けるかを、試作版で決めます（P-B6）。
6. ↶（取り消し）が、近くのページへ動いても消えません（今はページを移ると空になります）。良くなる所です。

8. 「このページ」の PDF に、隣のページからはみ出して入ってくる線も、紙の中の部分が出ます（P-B8）。
9. 線がとても多いと、隣のページが「見るだけ」になったり、1 ページずつに戻ったりします（上の「保存」の 3 つ目）。→ 目安の本数は、いまの本数（P-B9）と試作版で決めます。

### 2.4 しくみの細部

1. **焦点と題名**: 焦点 = 画面の真ん中の x（`(offset.x + 画面の幅 / 2) / 倍率`）を含むページ。境目を 5〜8 % 越えてから切り替える（境目の上で題名が行ったり来たりしない。数字は契約で決め、KitChecks で固定）。題名の文は今の `PageNavigation.title`。「最後に開いたページ」（`remember()`）は止まったときの焦点。
2. **合成レイアウト `SpanLayout`**（`PageLayout` に従う）:
   - `pageId` = 仮想 id `span~<kind>~<n>`。**窓をずらしても変えない**（変えると `InkCanvasView.swift:599` で新しい台帳になり、↶ と位置が消える）。
   - `cells` = 各ページのマスを `<pageId>|<マス>` にし、x に原点を足したもの。
   - `inkCell(forCenter:)` = まず中心の x で持ち主のページを選び（半開区間。境目ちょうどは右のページ）、そのページの `inkCell` を局所座標で呼ぶ。帯の右端（右隣のページが窓に無い所）では、今の単独ページの規則（`x == 1400` は最後の列）のまま。
   - `hit`・`dayAt`・`eventRange`・`snapRect`・`growsWithInk` = 前置を外し、点の下のページ（またはマス名のページ）に振り分ける。`band`・`bandTop` = 焦点のページ（縦の位置の補正用）。
   - `drop(center:)` = 点の下のページの局所座標で、そのページの `PaperGrowth.drop`（`PaperGrowth.tail(of:)` は前置した名前を知らないので、合成レイアウトにそのまま渡さない）。帯の外は `outsidePaper`。「見るだけ」のページ（§6.3）の上は `viewOnly`（捨てる）。
   - `onlyTailHeightChanged(old:new:)` = 帯の全ページについて「最後の欄の高さだけが変わった」かを判定する版。
   - 型を決め打ちしている所（`ZoomPolicy.overviewSize` `:63-71`、`PageNavigation.initialScrollX/Y`、`DateTap.target`、`newEventPlan` `CalendarRootScreen.swift:1330`）は、点の下のページに振り分けてから呼ぶ。
3. **仮想ページ**（`SpanComposer`）:
   - 本物のページを読んだら、まず **ページごとに `BandMigration.migrate`**（前置したマス名では `isBandCell` が false になり、仮想 id では何もしないので、まとめた後では効かない【実測】）。
   - 線の id・マス・墓標・知らない道具の線の鍵を `<pageId>|…` にする。128 バイトを超える id（Web から来た長い id。`InkStroke.isValidId` は 128 バイトまで、`InkPage.add`/`remove` はそれを超える id を黙って無視する【コード】）は、端末の中だけの別名 `<pageId>|~<n>` にする。
   - `v`・`updatedAt`・知らない最上位の項目は、仮想ページに入れず本物のページ（PageSlot）に残す。
4. **窓をずらす手順**（SwiftUI の更新の外、main actor の次のターンで）:
   1. 条件を確かめる（上の「ずらす」の条件。受け箱が空でなければ先に空にする）。
   2. 受け箱を空にする（全部の差分を PageSlot に当てる）。
   3. 出るページ: 安全網の merge（§2.4 の 5 の (c)）→ dirty なら保存。**保存に失敗したら、ずらしをやめる**（PageSlot も台帳もそのまま。次に止まったときにもう一度。案内は今の「手書きを保存できませんでした」を 1 回）。
   4. `ledger.pruneHistory(touching: 出るページ)`。
   5. `SpanComposer.shift`（出るページの鍵を外し、入るページを足す。入るページは先読みが済んだ PageSlot から。§2.4 の 10 の古さの確かめを通ったものだけ）。
   6. `ledger.reload(keepHistory: true)`（指紋の表を作り直す）→ 新しい `SpanLayout` で絵を作る → `contentSize` = 帯 × 倍率 → `contentOffset.x` を補正（行の高さが変わったときは焦点のページの `PageScroll.scrollDelta` で y も）→ 紙の位置 → 版つきの `PaperViewport` を同じターンで見出しへ（ずらした瞬間に見出しが 1 ページ分飛ばないように）。
   7. 入るページの予定を読む（§2.4 の 9）・`sync.pagesOpened`（まとめて 1 回、§2.4 の 10）。
   - 1.5（週・日）では絵は `ledger.relayout`（全部作り直す。週・日は線が少ない）。1.6（年）で「残る線は `PKDrawing.transformed(using:)` で平行移動だけ、入るページの線だけ作る」速い道を足す（25,000 本で 277 ms → 64 ms【実測、macOS】）。速い道では指紋の表を差分で保つことになるので、§2.4 の 6 の (d) のテストを必ず通す。
5. **書き戻しはページごとの差分**（見直しの指摘で約束を足した）:
   - キャンバスは台帳の日誌を `PageDelta`（ページ id・足した線・消した id・時刻・番号）に直して出す。画面は `PageSlot.page` に今と同じ `InkPage.add` / `remove` を当て、dirty にし、1.5 秒後に `sync.save`（今の `scheduleSave`・`saveNow`、`CalendarRootScreen.swift:1917-1938` と同じ）。**ページを丸ごと書き戻すことは無くなる**。
   - **(a) ためない**: 台帳を変えた同じターンで、日誌を差分にして受け箱 `SpanInbox` に入れる。受け箱は SwiftUI の状態ではない参照型で、画面とキャンバスが強い参照で持つ（`updateUIView` の中で走る ↶ ↷ やコマンド（`applyPending`）からでも、状態を変えずに入れられる）。受け箱は `deliver` で 1 回だけ空にする予約をし、空にするときは順番どおり全部当てる。画面は `onInkBoundsChanged`・ずらし・保存・裏へ回る・開き直し・全て消すの入口で、まず受け箱を空にする（差分が relayout より後に届くことは無い）。`detach()`（`InkCanvasView.swift:541-550`）で delegate を外す前にも、日誌を出し切って受け箱に入れる。
   - **(b) 間引かない**: 差分には `publishPage` の superseded の判定を使わない。差分は足し算と墓標だけで、id は二度と戻らない（↶ は新しい id の写しで戻す）ので、順番が入れ替わっても、2 回当てても結果は同じ【実測、V2Probe §2: 364 個の差分を 50 通りの順で当てて全部 `==`、全部を 2 回ずつ当てても `==`】。
   - **(c) 安全網**: 保存（`scheduleSave`・`saveNow`）とずらしのたびに、キャンバスの台帳から、仮想ページのそのページの範囲（前置を外し、`updatedAt` はその範囲の中の一番新しい時刻）を取り出し、`InkPage.merge` で PageSlot に混ぜる。和集合＋墓標なので線を失わず、取りこぼした差分を必ず回収できる【実測、V2Probe §3: どの差分を 1 つ落としても、merge で同じ中身に戻る。何も落ちていなければ中身は変わらない。PageSlot にだけある iCloud の線と墓標も残る】。merge の結果が `contentDiffers` のときだけ PageSlot を置き換えて dirty にし、「安全網で回収した」を記録する（回収が起きたら差分の道の不具合なので、Debug では止める）。丸ごと置き換える F5 とは違い、キャンバスが古くても何も消さないので、K-3 の趣旨に反しない。キャンバスが外れた後は、`detach()` のときに出した最後の範囲が受け箱に入っている。
   - **(d) 差分は、それを出したキャンバスのセッションにだけ当てる**: セッション（`SpanSession`）は、キャンバスが外れて受け箱が空になり、全ページを保存し終えるまで閉じない（開き直しでは、新しいセッションを作る前に古いセッションを「閉じかけ」にし、受け箱を空にして `saveAll()` してから捨てる）。ずらしで出るページは、受け箱を空にして保存してから外す。だから「窓に無いページへの差分」は起きない作りにする（起きたら当てずに記録し、Debug では止める）。第 1 版の「保存先から読んで当てて保存する」は消した。
   - 差分を当てて上がった版は、キャンバスが自分の差分だと分かるので読み直さない（今の `PageSignature` の役目）。外から来た変化は別の数（§2.4 の 10）で知らせる。
   - **仮想ページは保存・同期・書き出し・PDF に出さない**。画面が受け取るのはページごとの差分と範囲だけにし、型（`SpanVirtualPage`）で包む。Release でも入口で確かめる（§2.4 の 11）。
6. **削除の守り**（見直しの指摘で足した。`applyCanvasChange`（`InkLedger.swift:306-318`）は「指紋の表にあって、キャンバスに無い id」を全部墓標にし、台帳に無い id にも墓標を付ける（`InkPage.remove` は無い id にも墓標を付ける、`InkPage.swift:125-141`）。その墓標は、他の端末で生きている同じ id の線にも merge で勝つ【実測、V2Probe §4】。1 度の取り違いで、画面に出ていないページの線が全端末から消えうる）:
   - **(a)** 台帳が削除を日誌に書くのは、その時点で仮想ページで生きていた id だけ。それ以外は墓標にも日誌にもせず、Debug では assert、Release では記録を残す【実測、V2Probe §4: 窓から出たページの指紋の取り残しのような id は日誌から外れ、他の端末の線は残る】。
   - **(b)** キャンバスの差分で線が減るのは、消しゴムのときだけのはず（投げなわの移動・↶ ↷・コマンド・指の点消しは台帳の関数か `setDrawing` を通り、`isApplyingDrawing`・`isMovingSelection` の門で外れる。PencilKit 自身の ↶ は `undoManager.removeAllActions()` で止めている、`InkCanvasView.swift:1415-1418`）。だから道具が消しゴムでないのに線が減ったら、墓標にせず、絵を台帳から作り直して記録する（台帳の変更 5）。消しゴムでも、1 回の変化で消える線が多すぎる（1 回に 50 本を超える、または窓のあるページの生きている線の半分以上でかつ 20 本以上）ときは同じ扱いにする（PencilKit の線ごとの消しゴムは、1 回の変化で数本ずつしか消さない【推論。試作版で数を測って契約で決める】）。投げなわで選んで「削除」は台帳の `removeStrokes` を通るので、この制限を受けない。
   - **(c)** 窓に無いページへ差分を当てる道は作らない（§2.4 の 5 の (d)）。古い番号（§2.4 の 7）の差分は捨てる。
   - **(d)** 1.6 の速い道（平行移動のずらし）でも、XCTest で「ずらした直後に絵を台帳へ戻しても増減が 0」「出たページの指紋が表に 0 件」を固定する（§11.3 の項目を速い道にも広げる）。
7. **ページの状態の組 `PageSlot` と `SpanSession`**（今の `page`・`paper`・`pageDirty`・`saveTask`・`capNoticedPageId`、`CalendarRootScreen.swift:131-206` を 1 つの型に）:
   - `SpanSession` は PageSlot を N 個と受け箱を持つ。1.9 の書ける終日欄（`wb-`/`db-`）は、同じ窓・同じ横位置・同じ倍率でもう 1 つの `SpanSession` を持てばよい（§9.3）。
   - **`saveAll()`**: 受け箱を空にする → 各ページに安全網の merge → dirty なページを全部 `sync.save`。失敗したページは dirty のまま残し、まとめて 1 回案内する。
   - **`cancelAll()`**: 全ページの保存の予約を止め、受け箱を捨て、番号を進める。
   - **番号（epoch）**: 差分とセッションに番号を持たせる。「全て消す」とアカウントの切り替え（「消して始める」）で番号を進め、古い番号の差分と保存の予約は捨てる（`SyncEngine.workEpoch` と同じ考え方、`SyncEngine.swift:93, 286`）。
   - **今は 1 ページ分の呼び口を、全部 `SpanSession` に替える**: 裏へ回る・非アクティブ（`:1028-1031`）→ `saveAll()`。`show()`（`:1092`）→ `saveAll()` してから開き直す。書き出しの前（`openExport` `:1618-1619`。JSON は store から読む）→ `saveAll()`。アカウントの「残す」（`:1722`）→ `saveAll()`。「全て消す」（`:1476-1481`）と「消して始める」→ `cancelAll()`。取り込み → 前に `saveAll()`、後で開き直す。
   - **出るページの保存に失敗したら、ずらしをやめる**（§2.4 の 4 の 3）。今も「保存に失敗したままページを移ると消える」穴があるが、B では止まるたびにずらすので、ずらしの側で必ず止める。
8. **キャンバス（`InkCanvasView`）で変える所**:
   - 入力を「窓の状態」（版・帯・各ページの版・`SpanLayout`・紙の中身・受け箱）にする。1 ページの道の入力（今の page・layout・Binding）はそのまま残す。pageId の門（`:590`）と `PageSignature`（`:274-286`）は仮想 id でそのまま働く。
   - scroll の delegate に `scrollViewWillBeginDragging`（はじきの起点）・`scrollViewWillEndDragging`（はじきの行き先）・`scrollViewDidEndDecelerating`・`scrollViewDidEndScrollingAnimation` を足す。ずらしのきっかけはこれらと、`DidEndDragging(willDecelerate: false)`・ペンが離れて落ち着いた後・ピンチの終わり・回転・投げなわの選択が解けたとき。取りこぼしに備えて見張りのタイマー。
   - `screenNewStrokes`（`:1499-1535`）: 紙の外の判定は `SpanLayout.drop`、線の予算は持ち主のページごと（前置した名前で数える）、「メモ欄はここまでです」と予算の案内はそのページの id で。⑦ は前置を外して `isTail`。
   - `canvasViewDrawingDidChange`: 台帳の変更 5 の「作り直しが要る」が返ったら、`setDrawing(ledger.drawing())` で絵を戻し、記録する（§2.4 の 6 の (b)）。
   - `contentSize` = 帯 × 倍率。横の中央寄せの余白は、帯が画面より広い間は 0。
   - 投げなわの候補・動かす絵・移動の上限（`overlay.pageSize`）は帯で。最後の欄だけ伸びたときの軽い道は `SpanLayout.onlyTailHeightChanged`。
   - ◀ ▶ と「今日」は、画面からの命令（今の `commandTrigger`）でキャンバスがアニメーションで横にすべる。
   - キャンバスの持ち手 `SpanCanvasHandle`（`slice(pageId:)` で仮想ページのそのページの範囲を返す）を画面に渡す（安全網用）。
9. **画面（`CalendarRootScreen` → `SpanSession`）で変える所**:
   - 題名・`remember`・`sync.pagesOpened` を焦点と窓から決める。今の時刻の線はページごと。種類の切り替え・日付のタップ・遠い今日・全て消す・取り込みは `show(kind:focus:)` を「焦点の周りに新しいセッションを作る」として残す。
   - `applyRemote` を窓のページに振り分ける（窓のどれか、または先読み中のページなら、その PageSlot に merge → `BandMigration.migrate` → 端末にしか無い線があれば保存 → 外から来た版を上げてキャンバスへ）。それ以外は無視（保存先にある）。
   - **予定はページごとに読む**（見直しの指摘で変えた。第 1 版の「窓の全ページの `dayRange` の和を 1 回で読む」は、年の窓（5〜9 年）で EventKit の 4 年の上限に当たり、右側の年の予定が知らせなしに 0 件になる。11 インチ横・iPad 13 横・iPhone 横の年の窓 7〜9 年では、一覧の右端に見えている次の年の 1 月にも出ない）:

11. **仮想の名前を外へ出さない守り（Release でも）**（第 1 版は assert だけで、Release では消えた。前置した名前のマス `w-…|grid` が本物のページに入ると `isValidId` を通り、どの版のレイアウトにも無いマスなので F1 により「描かず・消さず」の線として全端末に永久に残り、線の予算にも数えられる。仮想 id `span~week~3` はファイル名で `span_week_3` になり F2 で全端末へ運ばれる【実測、V2Probe §5】）:

    - K-10 を足す（§4.2）。
12. **ページのファイルの「読む・merge・書く」は直列**（見直しの指摘で足した）:
    - 今は `SyncEngine.save`（`:136-158`）・`mergeRemote`（`:625-652`）・push の衝突の merge（`:720-727`）・`importPages`（`:316-327`）の「読む → merge → 書く」が、全部 main actor の上で途切れずに走る（間に await が無い）。
    - **1.5 では変えない**（全部 main のまま。先読みは読むだけ）。

## 3. ページの種類ごとの見え方

### 3.1 どの種類でも同じこと

- **並び**: 同じ種類のページが、すき間なく横 1 列に並ぶ（左が前、右が次）。紙の幅は今のまま（日 1,000、週・月・年 1,400 lu）。境目は、週・日・年では次のページの数字の列（時刻 64・72 lu、日付 56 lu）、月では少し濃い縦線。今まで左右の机の色の余白だった所に、隣のページが見える。
- **書く・動かす**: Apple Pencil はどこでも書ける（境目の上も）。ペンが紙に触れている間は紙は動かない（PencilKit の既定）。1 本の線の長さは、書いたときに見えていた幅まで。

| 端末と設定 | 指 1 本 | 指 2 本 | Apple Pencil |
| --- | --- | --- | --- |
| iPad・「指でも書く」オフ（既定） | 上下左右に動かす（一覧でも。今は一覧で横に動かない） | ピンチ・動かす | 書く |
| iPad・「指でも書く」オン | 書く | 動かす・ピンチ | 書く |
| iPhone・「指でも書く」オン（既定） | 書く | 動かす・ピンチ（M4B-21） | （Duo だけ）書く |
| iPhone・「指でも書く」オフ | 上下左右に動かす | ピンチ・動かす | （Duo だけ）書く |

  - 方向のロックは今のまま（指を斜めに動かしても、上下か左右のどちらかに動く）。◀ ▶ はいつでも使える。
  - 手のひらや指の横ずれへの手当ては §3.6。
- **はじいたとき**（P-B5 で確定）: 一覧（1 ページがほぼ画面の幅）では、はじくと隣のページへ（めくる感じ）。ゆっくり動かせば好きな所で止まるので、境目を画面の真ん中に置いて書ける。ページの端が画面の端の 6 % 以内で止まったら、ぴたりとそろえる。拡大中は自由に流れ、窓の端の手前で止まる。
- **◀ ▶**: ちょうど 1 ページ分、横にすべる（同じ列・同じ時刻・同じ高さのまま。境目を真ん中にしていたら、境目が真ん中のまま 1 ページずれる）。行き先が窓の外なら、窓をずらしてからすべる。
- **今日**: 今日のページが窓の中ならすべって行き、遠ければ今と同じく開き直す（一覧なら真ん中、拡大中なら今日の列と今の 1 時間前）。
- **日付のタップ・ダブルタップ・種類の切り替え**: 今と同じ（行き先を真ん中にして開き直す）。点を「そのページの中の点」に直してから今の関数（`DateTap`・`hit`・`dayAt`）に渡す。
- **一覧の倍率**（見直しの指摘で既定を変えた）: 今と同じ「1 ページの一覧の矩形が入る倍率」（fitAll）。**iPhone 横もそのまま**で、24 時間全部が入り、左右に前後の週・日・年が小さく並ぶ（週 0.107 で約 5.9 週、日 0.085 で約 10 日、年 0.124 で約 5 年が並ぶ）。本人は M4c で「一覧で見えないと予定の全体が掴みにくい」と頼んでいる（`M4C_CONTRACT.md:5`）ので、それを保つ。
  - 第 1 版の「横に並ぶのは週・年 3 ページ、日 5 ページまで（上限）」は、iPhone 横の一覧を約 2 倍の大きさにし、24 時間の半分ほどしか入らなくする（週 0.107 → 0.208 で 51 %、日 0.085 → 0.175 で 49 %、年 0.124 → 0.208 で 59 %）。既定にはせず、試作版で重さとちらつきを測ってから、要るときだけ本人に聞く（P-B6）。
  - 上限の代わりの軽い形も比べる: 倍率は今のまま、線を全部作るのは前後 1 ページまでで、その外は「見るだけ」の絵（§6.3 の段 1 と同じ作り）。
  - 帯全体の幅で倍率を決めることはしない（13 インチ縦の月で約 0.73 が約 0.24 まで縮む）。
- **一覧より縮めて見渡す**（P-B10。既定はしない）: 下限を「2〜3 ページが入る倍率」まで下げると、何ページも見渡せる。既定の一覧（開いたときの大きさ）は 1 ページのまま。見本の画像（11 インチ縦・横、iPhone）で見てもらってから決める。下げるなら窓は V に合わせて大きくなる（§6.2）。
- **高さのそろえ**（§3.2〜3.5）は、窓の中のページの「自然な高さ」の最大を下限にして、各ページのエンジンに渡す。
  - 横に動いて窓がずれても下限は下げない（見えている行が縮まない）。ただし、書いたページで欄が縮む（消しゴムで消して、そのページの自然な高さが下がる）ときは、1.1 と同じく白紙も縮む（下限を、窓の中の自然な高さの最大まで下げる。M7_PLAN P-6 の A「消せば白紙も縮む」）。開き直し・回転・ピンチの終わりでも決め直す。
  - 動くのはマスの位置と大きさだけで、マスの意味（左上からの相対座標）は変えない（K-4）。のばす向きは「手書きで行が伸びる」と同じなので、古い端末でも、のばした所に書いた線は見える（古い端末はその行を「手書きの下端 ＋ 12」まで伸ばす）。
- **一覧の大きさと終日帯の高さ**: 週・日・年は、そろえた高さで決める。**月の一覧の倍率は、そのページ自身の（そろえる前の）格子の高さで決める**（見直しの指摘で変えた。隣に予定の多い月があるだけで、iPad 縦の月が幅ぴったりより小さくなるのを防ぐ。13 インチ縦では、窓に格子の高さが約 1,500 lu を超える月があると 0.737 より小さくなっていた【推論・計算】）。そろえで伸びた最後の行とメモ欄は、今のメモ欄と同じく下へすべらせて見る。窓をずらして高さが伸びても、表示中の倍率はその場では変えない。決め直すのはピンチの終わり・回転・開き直し。横に動いただけで倍率が変わることは無い。
- **固定見出し・終日帯**: 窓のページの列を原点付きで並べる（`PaperRow` は列の配列を並べるだけの作り、`StickyHeaderView.swift:292-333`）。終日予定のレーンは、窓の全部の日をまとめて詰める（`AllDayBandEngine` に「日の並び」を受ける口を足す）。週ごとに詰めると、週をまたぐ予定のレーンが境目で入れ替わる【実測】。レーンの数は横に動いている間は変えない（窓をずらすときに決め直し、セッション中は減らさない）。
- **初めての案内**（見直しの指摘で足した。iPhone 縦の一覧では週・月・年がほぼ 1 ページで隣が見えず、横へは 2 本指で動かすので、中心の機能に気づきにくい）:
  - 横につないだ種類を、更新後に初めて開いたとき（端末ごと・種類ごとに 1 回）、紙の上の端（終日帯のすぐ下）に小さな札を出す（下に出すと、日の自由メモや月のメモ欄を隠すため）。8 秒で消える。触れても消える。写真モードと設定オフでは出さない。
  - 文（週の例。日・年・月は語を替える）:
    - iPad・「指でも書く」オフ:「前後の週が横につながりました。指で横にすべらせると、となりの週が出てきます。境目をまたいで、そのまま書けます。」
    - 「指でも書く」オン:「前後の週が横につながりました。2 本指で横にすべらせると、となりの週が出てきます。境目をまたいで、そのまま書けます。」
  - 絵（`b2-iphone.svg`）の黒い札はこの案内。

### 3.2 週（1.5）

- 並び: 先週の日曜 │ 次の週の時刻の列（0:00〜23:00）│ 月 火 … 日 │ … 。0 時〜24 時の横線は一直線（どの週も 1,400 × 1,920 lu）。そろえる物は無い。
- 時刻は上から下なので、日曜の夜から月曜の朝へは、左の週の日曜の下の方から、右の週の月曜の上の方へ斜めの線になる（今の週の中で月曜の夜から火曜の朝へ書くのと同じ形）。
- 見出し: 時刻の列の見出しに、その週の月曜の月（「11月」）。1 月 1 日を含む週は年（「2027」）。
- 書ける例: 日曜 22:30 の夜行バスから月曜 6:30 へ 1 本の線（保存されるのは中心のある週）。土〜火の「荷造り → 引っ越し」の矢印。
- 一覧で見える量: iPad 11 縦 1.20 週（左右に約 70 pt ずつ前後の週）、11 横 2.70 週、13 縦 1.26 週、13 横 2.33 週、iPhone 縦 1.02 週、iPhone 横 5.85 週（今の一覧のまま）。
- 1.3 の「指で予定」は「前後の週へはドラッグしない（日曜の列の右で止まる）」計画（M7_PLAN §2.9.5）。帯では、端での自動スクロールを横にも続け、隣の週の日へ運べるようにする（1.5 で）。

### 3.3 日（1.5）

- 並び: 前の日の右のメモ列（660〜1,000）│ 次の日の時刻の列（0〜72）│ 時間軸 │ メモ列 │ … 。0 時〜24 時の横線は一直線。
- 時刻は上から下なので、「日の右に次の日」でも、夜中（24 時の線）の右どなりは次の日の 24 時で、次の日の 0 時は右の上の端にある。夜中をまたぐ予定（22 時から翌朝 6 時の夜勤）は、左の日の下の端から右の日の上の端へ、画面の高さいっぱいの斜めの線になる（絵 `b2-iphone.svg` の ④）。
- 24 時の下の「自由メモ」（`extra`）: どの日も同じ高さ（24 時の下）から始まるので、横にまっすぐ 1 本の帯になる。窓の中で一番長い日に合わせて **下の端をそろえる**。短い日の下も白い紙のまま続き、そこに書くとその日の欄が伸びる（上限 6,000 lu と「メモ欄はここまでです」はページごと）。
- 書ける例: 夜勤の斜めの線。右のメモ列から次の日の時間軸へ横に続けて（同じ時刻のまま次の日へ）。自由メモで「土日の予定 →」を何日にもわたって。
- 一覧で見える量: iPad 11 縦 2.10 日、11 横 4.72 日、13 縦 2.22 日、13 横 4.07 日、iPhone 縦 1.80 日、iPhone 横 10.23 日（今の一覧のまま）。ダブルタップは今と同じく何も起きない。

### 3.4 月（1.7）と、並べ方の決め方

**事実**【コード・実測】
- 月の表はいつも 6 行 42 日（`MonthLayoutEngine` は `grid.allRows` を回す。`MonthLayout.swift:26`、`MonthLayoutEngine.swift:61`）。
- 隣の月の表と 7 日か 14 日重なる（例 10 月の表は 9/28〜11/8、11 月の表は 10/26〜12/6）。同じ日付が 2 つのページに別のマスとしてあり、手書きも別々（`m1-2026-10` の `2026-11-01` と `m1-2026-11` の `2026-11-01`）。
- 表の中は「横 = 次の日、下 = 次の週」。横に並べると、同じ行の右隣は 4〜5 週あとの日（10 月の 1 行目 9/28〜10/4 の右は、11 月の 1 行目 10/26〜11/1）。**表と表の間では日付が続かない。**
- 行の高さは月ごとに違う（予定と手書き）。メモ欄の上端も月ごとに違う。

**決めた形（既定）: 月のカレンダーを横に並べて貼る ＋ メモの帯**
- 10 月の表の右に 11 月の表。境目は濃い縦線。
- **メモ欄の上の端と下の端を窓の中でそろえる**（格子が短い月は最後の行をのばす。上限は月の行 1,200 lu）。メモ欄が横に 1 本の帯になり、「年末までに: 大掃除 → 年賀状 → 帰省の切符」のように、月の境目をまたいで続けて書ける。
- **格子の行はそろえない**（左右の行はもともと別の週。横に動いても格子が伸び縮みしない）。
- **月の表の上で日付どおりに続けて書けるのは、今と同じく 1 つの表の中**（前後の月の薄い日まで）。例: 10/30〜11/2 の旅行を 10 月の表に書くなら、10 月の表の 10/30 から薄い 11/1 まで矢印を引き、次の行の薄い 11/2 へ続ける。**10 月の表の薄い日に書いた線は、すぐ右に並んだ 11 月の表の同じ日（10/30〜11/2）には出ない**（同じ画面に 11/1 のマスが 2 つ並ぶことがある。11 インチ横の一覧など）。絵 `b2-month-ipad11.svg` の ④。
- 日付どおりに月をまたぐ予定は週のページで書く（週は日付が横に続く）。月の形でも日付どおりに続けたいなら、B の形では作れない（以前の「計画の紙」の役目）ので、本人に確かめる（P-B11）。
- 前後の月の薄い日は今のまま（両方の表に出る。今日の印も薄い方にも出る）。隠す形は採らない（そこにある手書きが「見えないが消えない」状態になる）。目立たなくする形（全部が次の月の日の行、10 月の表なら 11/2〜11/8 の行を低くする。手書きがある行は、今と同じく手書きの分だけ高くなる）は P-B4 で残す。
- 見出し: 曜日の行の、各月の表の左端に月の名前の札（「11月」）。左へ出ていった月の札は画面の左端に残す（絵と同じ）。
- 一覧で見える量: iPad 11 縦 1.00 か月（今と同じ幅ぴったり。指で横にすべらせると隣の月が出てくる）、11 横 1.42 か月（左右に前後の月の表が約 1.5 列ずつ、行の高さがずれたまま見える。予定や手書きで行の高い月は倍率が少し下がり、2 列ほどになる）、13 縦 1.00、13 横 1.23、iPhone 縦 1.00、iPhone 横 2.85。

**見本の画像で選んでもらう 3 通り**（P-B3。CI の写真で、同じ見本のデータで並べる。11 インチの縦・横）
| 形 | 見え方 | 良い点 | 気になる点 |
| --- | --- | --- | --- |
| **ア メモ欄だけそろえる**（既定） | メモ欄の上下をそろえる。格子の行は各月のまま | 月をまたいで書く場所がはっきりする。格子が動かない | 境目で格子の横線がずれる。最後の行がのびる月がある |

### 3.5 年（1.6）

- 並び: 2026 年の 1〜12 月 │ 2027 年の日付の列（1〜31）│ 2027 年の 1〜12 月 … 。見出しの日付の列に「2027」（左へ出ていった年は画面の左端に「2026」）。

- 一覧で見える量: iPad 11 縦 1.13 年（左右に前の年の 12 月と次の年の 1 月が少し）、11 横 2.51 年、13 縦 1.19 年、13 横 2.19 年、iPhone 縦 1.00 年、iPhone 横 5.05 年（今の一覧のまま）。

## 4. データ（持ち主・保存の形・互換・移行）

### 4.1 持ち主と保存の形

- 境目をまたいだ線は、**外接矩形の中心の x が入るページ**の線として **1 本のまま** 保存する。帯の中は半開区間で、境目ちょうどは右のページ。ページの中のマスは今の `inkCell(forCenter:)`。持ち主は日付ではなくページの矩形で決める（月の前後の日は 2 つのページにある）。
- 持ち主は書いた端末が書いたときに 1 回だけ決め、レイアウトや予定が変わっても決め直さない。
- 点は持ち主のマスからの相対座標（0.1 lu）。隣の紙の上に出た部分も **切らずに** 持つ（x が負、または紙の幅を超える）。座標の上限 ±100,000 lu（`InkStroke.swift:25`、1.0 も同じ `InkStrokeV10.swift:24`）に対して、窓は最大でも約 15 × 1,000 lu（iPhone 横の日）。
- どのページの紙にも中心が無い新しい線（帯の外）は、今の M4C-25 と同じく捨てる。
- 例【実測】: 週の夜行バス（日曜 22:30 → 月曜 6:30）は `w-2026-11-02` の `grid`、x −115〜179。日は `d-2026-11-02` の `grid`、x −180〜300。月のメモの線は `m1-2026-11` の `memo`、x −160〜260。年は `y-2027` の `01-20`、x −128〜70（日付の列に中心がある線は翌年 1 月のマスに入り x が負になる、1.0 からの規則）。どれも InkPage の JSON の往復で `==`。

**採らなかった持ち方**
| 持ち方 | 採らない理由 |
| --- | --- |
| 書き始めのページ | マス決め・投げなわの移動・Web 版の取り込み・Web 版の週の移し替えは全部「中心」で決めている。規則が 2 つになり、古い端末で見えない部分が大きくなる |
| 境目で 2 本に分ける | 古い端末と 1 ページの PDF でも両側が見える利点はあるが、消しゴムで片側だけ消える、境目に継ぎ目が出る（マーカーは重なりが濃くなる）、1 本書くたびに 2 ページを書き換える、動かすたびに分け直す |
| 境目専用の別ページ | 新しいページ id が要り、古い端末ではどちらのページにも出ない |

### 4.2 K-1〜K-10 との対照

| 規則 | B で |
| --- | --- |
| K-1 新しい名前に `allday` を使わない | **新しいマス名・ページ id を作らない**。仮想 id `span~…` と前置した名前 `<pageId>|…` は端末のメモリの中だけ。`BandMigration` は本物のページごとに、まとめる前にかける |
| K-2 同じ id の線を別のマスへ付け替えない | ページをまたぐ移動（投げなわ、1.3.1 の「予定と一緒に動く手書き」）は、行き先に新しい id、元に墓標。`makeId(cell)` で写しは必ず行き先の名前を持つ【実測】 |
| K-3 1 つのページ id に 2 枚のキャンバスで書かない | 種類ごとにキャンバスは 1 枚で、窓の中の同じページ id は 1 回だけ。2 本の道は同時に同じページを開かない（切り替えは全部保存してから開き直す）。書き戻しはページごとの差分と、和集合の安全網だけで、ページを丸ごと上書きしない（F5 の危険そのものが無くなる） |

### 4.3 古い端末（1.0〜B の前の版）・Web 版での見え方（許す範囲）

- **消えない・壊れない・動かない**【実測】: 1.0 の凍結の写し（Compat10）で、4 種のページのはみ出す線（月は右へ 250 lu、週は左へ 300、年は 12 月から右へ 288、日は右へ 300）を確かめた。1.0 で読める（±100,000 の内）・`BandMigration` で動かない・描く対象と投げなわの候補に入る（`LedgerV10.drawnIds`）・merge で残る・**1.0 が書き戻すバイトは同じ**・新しい書き出しを 1.0 で取り込んでも残る。古い端末が捨てるのは、その端末で新しく書いた紙の外の線だけ（M4C-25）。
- **見え方が欠ける範囲（許す）**:
  - またいだ線は、保存されたページにだけ出る。もう一方のページには、入ってくる部分も出ない。
  - 保存されたページでの見え方: iPhone（一覧で紙が画面の幅いっぱい）では、紙の端から先は画面の外で切れて見える。iPad の一覧（左右に机の色の余白）では、余白の上にはみ出して描かれる（PencilKit は `contentSize` の外の点も描くと見込む）か、余白の所で切れる【推論】。CI の 1 ページ表示の写真（iPhone と iPad）で確かめてから、新機能の文と SUPPORT の文を決める（§8.1）。
  - 古い版の PDF では紙の端で切れる。
  - 「横につなげる」をオフにした端末も同じ見え方。
- 古い端末の操作: 見えている部分に触れれば 1 本ごと消せる・選べる。**古い版で消すと、新しい版でも消える**（墓標。正しい動き）。古い端末の投げなわの移動は 1 ページの紙の中に止められる（`LassoGeometry.clampedMoveDelta`）ので壊れない。
- **B を出す途中の版どうし**（1.5 で週・日だけつながっている端末）が、1.6 以降の端末が書いた年をまたぐ線を見ると、古い端末と同じ見え方になる。データは同じ。
- **Web 版**: アプリの線を読まない（Web 版がするのは `tegaki-web-export` を書き出すことだけ。`tegaki-app-export` を読むコードは無い）。影響は無く、Web 版は変えない（他の Pages を公開しない約束にも触れない）。Web からの取り込み（4 種のページ、`WebImport.swift:278-319`）も変わらない。
- 新機能の文に入れる行（K-8）:「iPad と iPhone の両方をこの版にしてください。古い版では、ページをまたいで書いた線が片方のページにだけ出ます（消えてはいません）。古い版でその線を消すと、こちらでも消えます。」（iPad での見え方の 1 文は §8.1 の写真の後に足す）
- 既存のデータにも紙の外へはみ出した点はありうる（端を越えて書いた線、Web 版の週の始まりの移し替えの残り）。B では、それが隣の紙の上に見えるようになる。データは変わらない。

### 4.4 移行

- **無し**。新しい名前も形も無いので、既存の線は 1 本も動かない。月・年・日のそろえも位置の変更だけで、保存されるものは変わらない。
- **B より前の版への約束**（1.3 の契約から入れる）: 紙の外の点を持つ線を、読み込み・merge・書き戻し・投げなわ・取り込みのどこでも捨てない・切らない。今のコードは守っているが、1.3（予定の長押しとドラッグ）・1.3.1（予定と一緒に手書きを動かす）が `Ink/*` を触るので、はみ出す線の fixture を互換テストに先に入れて、途中の版が B の線を壊さないことを確かめる。

## 5. 同期・取り消し・投げなわ・消しゴム・予定・PDF・写真モード

### 5.1 同期（iCloud）

- **記録の形は変えない**: 1 ページ = 1 件の記録で `recordName = pageId`（`InkPageRecord.swift:32`）。merge もページごと。`InkPageStore`・`InkPageRecord` は変えない。`SyncEngine` に足すのは 2 つの口だけ（1.5、足すだけで今の関数は変えない）: `pagesOpened(_:)`（§2.4 の 10）と `onRemoteDelete`（下）。1.6 で保存を主スレッドの外へ出すときは §2.4 の 12 の直列の約束を守る。データのコードの凍結表を、契約に列挙した手順で更新する。
- `sync.onRemoteUpdate` は 1 本のまま（`SyncEngine.swift:68`）。画面は受け取ったページが窓のどれか（と先読み中のページ）なら、その `PageSlot` に merge → `BandMigration.migrate` → 端末にしか無い線があれば保存 → 外から来た版を上げてキャンバスへ（キャンバスは `mergeIn` でそのページの名前の範囲だけ混ぜ、↶ は残す）。それ以外は無視（保存先にある）。今は表示中の 1 ページしか拾っていない（`CalendarRootScreen.swift:1192`）。
- **他の端末の「全て消す」**（見直しの指摘で足した）: 記録の削除が届くと、今の `SyncEngine` はファイルを消して `onRemoteUpdate(空のページ)` を呼ぶ（`:605-617`）。画面は merge するので、メモリのページはそのまま残り、次にそのページへ書くと全部の線が iCloud へ戻る（1.1 の 1 ページの画面にもある小さな穴。B では窓の 5〜15 ページ分が戻りうる）。記録の削除は `cloudErase`（全て消す）でしか起きない【コード】。B では `onRemoteDelete(pageId)` を足し、画面は窓のページ（1 ページの道では表示中のページ）を空のページに置き換え、保存の予約を取り消し、キャンバスにそのページの範囲を空にさせ、↶ のそのページの分を捨てる（`pruneHistory`）。1 ページの道にもこの直しを入れる（「1 ページの道は 1.1 のまま」の例外。ファイルはすでに `SyncEngine` が消しているので、画面をそれに合わせるだけで、線を新しく消す道は増えない）。
- **ページをまたぐ操作は 2 件の記録になる**（移動・複数ページの削除・「予定にする」・その取り消し）。CloudKit へは 1 件ずつ届くので、ほかの端末では一時的に「2 本見える」ことがある。**行き先のページを先に保存する**（dirty の並びがそのまま送る順、`SyncState.swift:158-161`）ことで、なるべく「消えて見える」側を避ける（元のページがすでに送る待ちに入っているときは、`markDirty` が並びを変えないので順番を保てない。そのときも一時的に見え方がずれるだけ）。和集合と墓標なので最後には必ずそろう【推論。merge の性質から】。
- 墓標は **持ち主のページ** に付ける（消しゴムが触れた場所のページではない）。前置した名前で自動的にそうなる【実測】。
- 全て消す（F7）・アカウントの切り替え・取り込み: `cancelAll()` または `saveAll()`（§2.4 の 7）の後、新しいセッションで開き直す。

### 5.2 取り消し（↶ ↷）

- 窓全体で 1 本の履歴（台帳は 1 つなので自然にそうなる）。今はページを移ると ↶ が空になるので、それより長く残る。1 回の ↶ が 2 ページを変えてよい（ページをまたぐ移動は 1 歩で戻る）。
- 窓から出るページにかかわる操作と、それより古い操作は捨てる（`pruneHistory`）。捨てないと、↶ が窓の外のページに線を戻し、画面には何も起きない【実測、付録 B-1 §6】。前後 R ページ以内（ふつう 2）にいる間は残る。
- **予定の取り消しとの組**（見直しの指摘で足した）: 1.3 の計画ではツールバーの ↶ が「予定の変更と手書きのうち新しい方」を戻し、1.3.1 では「予定と手書きを一緒に」戻す（M7_PLAN §2.9.6）。`pruneHistory` は台帳の InkOp しか見ないので、そのままだと出るページの手書きの操作だけを捨て、組の予定の取り消しを残す（↶ で予定だけが戻り、手書きは運んだ先に残る）。そこで:
  - 予定の取り消しの記録に、触れたページ id と組の印を持たせる（1.3 の契約で。段 0）。
  - `pruneHistory` で手書きの操作を捨てるとき、組の予定の取り消しも一緒に捨てる。逆に、予定の取り消しが期限切れで消えるときは、組の手書きの操作も消す。
  - テスト: 隣の週へ予定と手書きを運ぶ → 窓をずらす → ↶ は何もしない。
- 1.1 の「消しゴムのタップの取り消し」（`undoIfTopRestores`）と「指の点消し」の候補（`recentAdds`）は、前置した id のまま働く。

### 5.3 投げなわ・予定ツール・「予定にする」

- 投げなわは窓の全ページの線から選ぶ（50 % の規則は今の `LassoGeometry` を帯の座標で）。移動の上限は 1 ページの紙ではなく帯の紙（`overlay.pageSize` = 帯の大きさ、`InkCanvasView.swift:531, 749, 764`）。
- **選んでいる間は窓をずらさない**（見直しの指摘で足した）。ずらすと、出るページの線は `refreshSelection` で黙って選択から外れ、「削除」や「予定にする」が、選んだつもりの線の一部にしか効かない。選択は今どおり、別の所に触れるか道具を変えると解ける。解ければ次に止まったときにずれる。
- 移動の写しの持ち主は、移動後の中心で窓の中で決め直す。ページが変わるなら行き先に新しい id、元に墓標（今の `moveStrokes` そのまま）【実測】。
- 「予定にする」と予定ツール: 選んだ範囲の **中心のページ** のレイアウトで日時を決める（`eventRange` を局所座標で）。今の週のページは、枠の中心の列の日の時刻の予定になる（`WeekLayoutEngine.swift:142-148`）ので、境目をまたぐ枠も「中心の日」の予定になる（日をまたぐ予定は作らない。今と同じ）。予定を作った後に線を消すのは「まだ窓にあるページの線」だけ（`EventEditorRequest` の pageId を、前置した id の組に）。

### 5.4 消しゴム

- PencilKit の線ごとの消しゴム（`.vector`）は 1 枚のキャンバスの上でどこでも効くので、隣のページの線も、境目の上でもそのまま消せる（②の案で問題になった所が起きない）。
- 墓標は前置した id から持ち主のページへ。指紋の表はキャンバスに 1 つで、指紋の重なりを避ける「作成時刻を 1 µs ずらす」（`InkLedger.swift:95-119`）も窓全体で働く（月の見本の線が 2 か月で同じでも 2 本として扱える【実測】）。
- 1 回の変化で消える線が多すぎるときの守りは §2.4 の 6 の (b)。
- 1.1 の消しゴムの自動復帰はそのまま。

### 5.5 PDF

- 「このページ」の PDF は焦点のページ 1 枚。**隣のページから入ってくる線も重ねて** 描き、紙の矩形で切る（P-B8。問いではなく既定にし、本人には知らせるだけ）。日曜の夜から月曜の朝へ書いた線は、どちらの週の PDF にも、それぞれの紙の中の部分が出る。
- `PDFPageRenderer.render`（`:119-161`）と `ExportBuilder.exportPDF`（`:179-192`）に「隣の線とその横のずれ」の引数を足す。週・日の `grid` は全ページで同じ名前なので、`InkSnapshot` にはページごとに PKStroke を作ってから渡す。渡すのは本物のページ（PageSlot）から（仮想ページは渡さない、§2.4 の 11）。
- 紙は画面が見せているまま（そろえた後）のレイアウト（今の規則「画面が見せているまま」`PDFPageRenderer.swift:4-11` のとおり）。手書きの画像の 1,200 万画素の上限は今のまま。

### 5.6 写真モード（CI）

- 既存の引数の意味は変えない（`--screenshot-offset` は焦点のページの原点から）。引数を付けなければ今の写真は 1 バイトも変わらない。
- 足す引数: `--screenshot-span on|off`、`--screenshot-offset-x`（ページ単位。−0.5 で境目を真ん中に）、`--screenshot-span-shift N`（開いた後に N 回ずらしてから撮る）、`--screenshot-single-page`（古い版の見え方）、`--screenshot-overview-cap on|off`（P-B6 の比べ）、`--screenshot-overview-pages N`（P-B10 の比べ）。
- 撮る機種に iPad Pro 11-inch（本人の iPad の大きさ）を必ず入れる。
- 隣のページの見本は、ページごとに違う id で作る（今の月の見本は月が違っても同じ id、`ScreenshotMode.swift:379, 383, 387`。前置した名前なら混ざらないが、見本は分かりやすく分ける）。境目をまたぐ見本の線（持ち主が左のものと右のもの）を足す。compat11 の見本は変えない。

- R = ⌈(V − 0.05) / 2 + 1⌉（`SpanPlan.radius`）、窓 = 2R + 1 ページ【実測、V2Probe §7。V は調査のレイアウトの計算 `understand-geometry/window_and_caps.txt`】。R は「止まった後にしかずらさない」ので、はじきで 1 ページ進んでも端が見えないよう 1 ページの余裕を持つ。多くのページは手書きもファイルも無いので、読む時間はほぼ 0。
- 1 本の線は書いたときに見えていた幅までなので、持ち主は線のどの点からも V/2 ページ以内にある。窓の外のページが持ち主の、とても長い線の先は、近くまで動いて窓がずれるまで描かれないことがある（iPhone 横の一番縮めた状態で、何日にもわたる長い線を書いたときなど。まれ。データには影響しない）。
- 拡大中は V が小さいので、窓を倍率でも決める（拡大中は窓を小さくし、ピンチの終わりに広げる。広げ終わるまで端は机の色）ことを試作版の計測で検討する。最大倍率 × 一番広い窓の大きさを避けられる。

## 11. 試験

### 11.1 TegakiKit（この Mac の `swift build`・KitChecks と、CI の XCTest）

- `SpanPlan`: ページ番号とページ id の往復（4 種。年・月・週の境目、年をまたぐ週と日）、半開区間、焦点のヒステリシス、機種表の V と R（11 インチと iPhone 横の今の一覧を含む、§6.2）、ずらし量 = ページ数 × W × 倍率（例: 11 インチ縦の週 0.497 で −696 pt）、はじきの行き先、ファイルの大きさからの本数の見積もり（多めに数える）。
- `SpanLayout`: 4 種 × 境目の左・右・ちょうど・ガター（週・日・年）・帯の外・見るだけのページでの `inkCell` と `drop`（試作の「(1430, 100) → `m1-2026-11|2026-10-26`」を入れる）、`hit`・`dayAt`・`eventRange`・`snapRect`・`growsWithInk` の振り分け（前置名で呼んでも素の名前と同じ答え）、`onlyTailHeightChanged` のページごとの判定、窓 1 ページのときは今のレイアウトと同じ答え。
- `SpanName`・`SpanGuard`: 前置・分割・外す。実在の名前（Web の `~w1` の id、`allday:`・`band:`・`focus:`・`plan:`、各ページ id）は引っかからず、前置した名前と `span~` は必ず引っかかる【V2Probe §5 を移す】。前置を外した名前で `PaperGrowth.isTail`・`needsMoreRoom`・`growsWithInk` が素の名前と同じ答え【V2Probe §1 を移す】。
- `SpanAlign` とエンジンの下限: 入力を省けば今の出力と `==`（今の 24,446 件がそのまま緑）。入れたとき、月はメモ欄と最後の行だけ、年は行の y と高さだけが変わり、どのマスも x と幅が同じ。そろえた行の上端が全ページで同じ。下限の下げ方（ずらしでは下げず、消して縮むときは下げる）。月の一覧の倍率は、そろえる前の格子の高さで決まる。
- `SpanComposer` と `PageDelta`: 無作為の編集 300 回以上（新しい線・消す・ページをまたぐ移動・↶ の写し）で、差分を当てた本物のページ ＝ 本物のページを直接編集した結果（JSON まで）。順番を入れ替えても、2 回当てても `==`【V2Probe §2 を移す】。差分を 1 つ落としても、範囲の merge で同じ中身に戻り、何も落ちていなければ中身は変わらない【V2Probe §3 を移す】。名前の前置きが漏れない。編集しないページはバイト単位で同じ。同じ生の id が 2 ページにあっても 2 本。128 バイトを超える id の別名。`BandMigration` はまとめる前。
- K-10: 新しいページ id・マス名の生成器（`PageNavigation.pageId`・`CellKey` の作り方）が `|` と `~` を作らない。
