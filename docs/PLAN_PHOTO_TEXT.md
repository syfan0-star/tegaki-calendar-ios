## 1. 結論（おすすめ）

- **写真と文字の札を貼る機能は、1.5.1（月のページで予定を動かす）のすぐ後の独立した版「1.6」で出します（2027 年 6 月ごろ）。** 1.3（横につなげる）には混ぜません。

## 2. 何ができるようになるか

- 日・週・月のページの好きな所に写真を貼れます（チケット・地図など）。上から Pencil で書けます。
- 指で長押しすると持ち上がり、動かす・四隅で大きさを変える・消すができます（1.5 の予定と同じ操作）。写真は予定の下に貼られ、重なる所では予定が持ち上がるので、予定の無い所を押します。
- 直前の 1 回だけは「取り消す」か ↶ で戻せます（その後に手書きをすると、↶ は手書きの方を戻します）。
- 文字の札: 「文字」を押して開く画面で打った文が、紙の上に札として貼られます。
- iPad・iPhone で使え、iCloud で同期し、PDF にも出ます。VoiceOver では写真は「写真」、札は中の文と読み上げ、消す・動かすもできます。
- 写真を選ぶとき、アクセスの許可は求めません（選んだ 1 枚だけ受け取ります）。
- 古い版の端末では写真と札は見えませんが、消えません（古い版で「この端末の手書きを全て消す」を押すと消えます）。見えないまま上から書くと、新しい版では写真に字が重なります。両方の端末を新しい版にしてください。

### 3.1 データの形（凍結・古い版・同期・書き出し）

- **置く物は、ページの JSON の中の「新しい道具（tool）の 1 項目」にする**。例: `{"id","cell","tool":"photo"|"text","t","dev","rect":[x,y,w,h]（マス相対 lu）,"img":"<sha256>" または "text":"…"}`。計画の K-5 は「新しい情報は新しいマス・新しいページ・新しい tool にだけ入れる」と明記している（docs/M7_PLAN.md:91）。
- **1.0〜1.2 の端末は、知らない道具の項目を描かずに、そのまま残して書き戻す**（TegakiKit/Sources/InkModel/InkPage.swift:11-12, :296-307。1.0 の a21e469 でも同じ処理 `InkPage.swift:296-305`）。だから古い端末では「見えない・消えない」（K-8 と同じ、docs/M7_PLAN.md:98。ただし F7 の「全て消す」では消える、:80, :114）。merge は id ごとの和集合と墓標（InkPage.swift:173-183）、削除は墓標（:129-143）、変化の検出にも数えられる（:84-88）。
- **1.3〜1.5.1 の端末も同じでなければならない**。1.6 を出すころの「もう 1 台」は 1.3〜1.5.1 のことが多い。1.3 は Ink と InkModel を作り直すが、知らない道具の線を残す設計になっている（B_DESIGN.md:189, :245, :684, :874）。ただし今の fixture は `crayon`・`tape` だけ（TegakiKit/Sources/KitChecks/main.swift:535, :5140）。そのため 1.3 の契約の互換テスト（K-7）に、今のうちから写真の形の fixture（`"tool":"photo"`・`rect`・`img` を持つ項目と、`"tool":"text"` の項目）を入れ、横の道でも消えない・動かないことを確かめる。
- **動かす・大きさを変える＝新しい id の写し＋元に墓標**（投げなわの移動と同じ K-2、docs/M7_PLAN.md:88、Sources/TegakiCalendar/Ink/InkLedger.swift:488-521）。項目を書き換えないので、2 台で同時に操作しても最後は同じ形にそろう（ただし、2 台で同じ写真を同時に動かすと、写しが 2 枚になる。投げなわの移動と同じ。merge は和集合、InkPage.swift:149-203）。
- **最上位の新しい項目（例 `"photos": [...]`）にはしない**。最上位の知らない項目の merge は時刻ではなく文字列の大小で片方を選ぶ（InkPage.swift:185-192, :231-233）ので、2 台で同時に貼ると片方が消える。
- 線（pen・marker）に項目を足さない（F11、docs/M7_PLAN.md:84）。InkPage の `v` と書き出しの v1 は上げない（K-5）。
- **凍結（DATA_1_1.sha256 の 18 ファイル）**: この表は「1.2 の間だけの守り」で、1.3 が作り直す（docs/M7B_CONTRACT.md:490、tools/compat10/DATA_1_1.sha256）。写真と札は InkModel の凍結ファイルを変えずに作れる見込み: `unknownStrokes` は外から読み書きできる（InkPage.swift:30）、線の予算にも数えられる（TegakiKit/Sources/InkModel/StrokeBudget.swift:9, :122-124）。読み書きは TegakiKit の新しいファイルに置く。SyncEngine・InkPageRecord・InkPageStore も変えない（本体は別の仕組み、3.2）。InkCanvasView に要る「指の長押しの認識器」は 1.5 が予定のために足す（docs/M7_PLAN.md:396）ので、1.5 の後なら新たに開ける凍結は小さい【推定】。
- **互換テスト（K-7）**: 写真と札の入った fixture を 1.0 の凍結した写し（TegakiKit/Tests/Compat10、tools/compat10/run.sh:1-17）に通し、項目の数・中身・墓標が変わらないことを確かめる（docs/M7_PLAN.md:93-97）。
- 年のページは線の予算にいちばん近い（docs/M7_PLAN.md:104）。最初の範囲から外す理由の 1 つ（他はマスが小さすぎること）。
- **書き出し（JSON）**: 項目は今のままで入る（ページは `InkPage.jsonValue` そのもの、知らない道具の項目も数える。TegakiKit/Sources/InkModel/AppExport.swift:1-16, :47-50）。**写真の本体は JSON に入れない**。データファイル（JSON）の形は今のまま（写真は sha256 の名前で指すだけ）にし、写真の本体は別の画像ファイルとして同じ共有シートで添える（1 つにまとめるなら、フォルダーを NSFileCoordinator の .forUploading で zip にする。他社の部品は使わない）。同じファイルの最上位に写真を足す案はとらない。実際の取り込み口 `InkImport.parse` はファイル全体をメモリに読み（Sources/TegakiCalendar/Views/CalendarRootScreen.swift:1872, :1894）、知らない最上位の項目も JSON として全部解析する（TegakiKit/Sources/InkModel/InkImport.swift:66-70。1.0 の a21e469 も :68 で同じ）。そのため写真を入れると、古い版でも新しい版でもメモリが足りずに落ちるおそれがある。写真の取り込み（復元）は新しい版だけが行い、古い版は JSON の手書きだけを読む。規約 第 8 条 2 項の「書き出す手段」（docs/TERMS.md:80）に写真を含める。
- **PDF**: 今は紙（ベクタ）と手書き 1 枚の画像（Sources/TegakiCalendar/Export/PDFPageRenderer.swift:9-17, :122, :159）。紙 → 写真 → 手書きの順に描く。写真の分だけ PDF が重くなる。
- **伸びる欄**: マスの伸び（月のメモ・日の extra・月の行）と、PDF の伸びた欄の高さは、今は手書きの下端だけで決まる（`InkPage.inkBottoms` は線だけを数える、InkPage.swift:100-107。使う所は CalendarRootScreen.swift:433, :1372-1396、PDFPageRenderer.swift:62, :67）。凍結の InkPage は変えず、画面と PDF の側で「手書きの下端と、写真・札の下端の大きい方」を渡す。古い端末では写真が無いので欄は伸びないが、位置はマス相対なのでずれない（K-4）。
- **Web 版**: 変えない（docs/M7_PLAN.md:134）。Web からの取り込みは 4 種のページだけなので影響なし。

### 3.2 大きさと同期

- 今の保存は、ページ全体を毎回 JSON にして圧縮し、iCloud へ丸ごと送る（docs/M7_PLAN.md:82、Sources/TegakiCalendar/Sync/InkPageRecord.swift:21-29）。**写真の本体をページに入れると、1 本書くたびに数 MB を送り直す**。だから本体はページと分ける。
- **写真の本体は、iCloud の別の置き場（ゾーン。例 `tegaki-media`）の別の種類のレコードに置く**（CKAsset、名前は中身の sha256 で重複を防ぐ）。理由: 1.0〜1.2 はゾーン `tegaki` の変更を全部の項目つきで取り（Sources/TegakiCalendar/Sync/CloudKitDatabase.swift:12, :17, :123-131。`desiredKeys` を空にするのは名前だけのとき :125）、asset を全部メモリに読み（:386-393）、種類が `InkPage` でなければ捨てる（Sources/TegakiCalendar/Sync/SyncEngine.swift:601）。同じゾーンに置くと、古い端末が写真を全部ダウンロードしては捨てる。1.0 も同じコード（a21e469 の CloudKitDatabase.swift:12, :125, :391、SyncEngine.swift:601, :793 を確認）。
- **古い版の「全て消す」は `InkPage` のレコードだけを消す**（SyncEngine.swift:784-794）。別ゾーンの写真は残るので、新しい版は「どのページからも指されなくなった写真」を猶予（例 30 日）の後に消す掃除を持つ。猶予は、ふだんの削除で取り違えないための守りにだけ使う。「全て消す」（この端末で押したとき、他の端末からページの削除や写真のゾーンの削除が届いたとき）では猶予を置かず、端末の写真の写しもすぐ消す（他の端末からの削除で、ページのファイルはすぐ消している、SyncEngine.swift:610-616）。古い版の「全て消す」の後に残った写真のゾーンは、新しい版が次に開いたときに掃除する。新しい版の「全て消す」は写真のゾーンも消す。プライバシーポリシー §9 の約束（docs/PRIVACY.md:75）を守るため。
- 掃除の難しさ: 端末 A で消した直後でも、端末 B のまだ送っていないページが同じ写真を指していることがある。ふだんの削除ではすぐには消さず猶予を置く【推定。契約で設計】。
- **大きさ**: 貼るときに長辺 2,048 px 程度に縮めて HEIC か JPEG にする（1 枚 0.3〜1 MB の見込み【推定】）。CloudKit のレコード本体は 1 MB までで asset は数えない（Apple CKRecord 文書、DESIGN.md:674 と同じ前提）。asset 1 個は 50 GB まで（Apple の技術者の回答、2026 年 5 月、フォーラム。文書ではない）。プライベート DB は利用者の iCloud 容量に数えられる（Apple CKContainer 文書。docs/DESIGN.md:719 も「写真と共用」と書く）。容量不足のときは今と同じく端末に保存し続ける（docs/DESIGN.md:701）。
- **容量**: 容量の上限は口座全体で 1 つなので、写真で満杯になると手書きの同期も止まる（SyncEngine.swift:851-852 は同期全体を「容量不足」にする、CloudKitDatabase.swift:336-337）。写真は手書きと別の列で送り、容量不足のときは写真を止めて手書きを先に送る（それでも満杯なら手書きも送れない）。設定にこのアプリの写真の合計を出す。ページは届いたのに写真がまだ届いていない端末（送り途中・容量不足）では、枠と「写真はまだ届いていません」を出す。DESIGN.md:719 の「100 年分でも余る」は写真には当てはまらない（1 日 3 枚 × 0.3〜1 MB で 1 年に約 0.3〜1 GB）ので直す。
- 紙は 2×2 画面の窓で描き直す（Sources/TegakiCalendar/Ink/InkCanvasView.swift:32-33）ので、写真は縮小版を持って描く。1 ページの写真の数に上限（例 20 枚）を置く【推定】。
- **CloudKit の管理画面（CloudKit Console）**で、写真の新しいレコードの種類を作って Production へ配備する作業が 1 回要る。**これは本人の作業**（Apple のログインが要る。docs/M4_CONTRACT.md:11, :215、docs/M4.md:95-129 と同じ手順）。TestFlight のビルドも Production を使うので、TestFlight で試す前に済ませる（済むまでは TestFlight で写真のレコードを保存できない）。新しいゾーンはアプリが作るので配備は要らない。本人向けには 2 の「本人にお願いする作業」に書いた。

### 3.4 Pencil・投げなわ・消しゴム・↶ との取り合い

- 写真は**紙と手書きの間**（手書きの下）に置く。今の重なりは「紙 → 透明な PencilKit（スクロールも担当）→ 投げなわの層」（InkCanvasView.swift:31-39）。紙の層は凍結の外で、紙の中身は画面が作る（Sources/TegakiCalendar/Paper/PaperView.swift:5-30）。**写真を紙の中身として描けば、紙・PencilKit・投げなわの重なりは変えずに済む**【推定】。
- **予定との重なり**: 予定も紙に描かれる（月のバー・チップ、週・日の箱。PaperView.swift:8-13）。写真は予定の箱・バー・チップより下に描き、予定の文字を隠さない（既定）。長押しは予定と写真で同じ指の操作（1.5 の eventPressRecognizer、docs/M7_PLAN.md:396）なので、重なった所では予定が持ち上がり、写真は予定の無い所を長押しして動かす。この規則を契約に書き、表でテストする。
- **落とし穴（updatedAt）**: 台帳はページの写しを自分で持ち（InkLedger.swift:159）、線を書くたびにその写しを丸ごと画面へ書き戻す（CalendarRootScreen.swift:1119-1133、F5 docs/M7_PLAN.md:78）。キャンバスが外のページを台帳に読み直すのは「pageId・updatedAt・線の数・墓標の数」が変わったときだけで（InkCanvasView.swift:305-316, :856-861。1.0 の a21e469 も :231-237 で同じ）、知らない道具の項目（写真・札）は数えない。だから写真を貼っても updatedAt が変わらないと、次の 1 本で写真が画面のページから消える。保存の merge（SyncEngine.swift:136-143）と applyRemote（CalendarRootScreen.swift:1542-1552）で戻るが、線を書くたびにちらつく。他の端末から時計の遅れた写真が届いたときも同じ（merge は大きい方の updatedAt を残す、InkPage.swift:199）。写真と札の操作では必ず updatedAt を上げる。applyRemote でも、写真と札の id が変わったら updatedAt を上げる（または PageSignature に知らない道具の数を足す。これは InkCanvasView を変えることになる）。どちらにするかは契約で決め、XCTest に「写真を貼る → 1 本書く → 写真が残る」と「時計の遅れた端末からの写真」を入れる。
- Pencil は書くだけのまま（docs/M7_PLAN.md:63, :395）。写真と札は指で操作する。手のひらで動かない守り（:397）と、持ち上げ・動かす・離すと選択を解く流れ（:398-400）を流用する。
- **文字の入力欄は紙の上に置かない**。スクリブル（手書き→文字）が Pencil の線を横取りするため（docs/DESIGN.md:554-556）。予定と同じく、紙を覆うシートの中で打つ（シートではスクリブルが効く、docs/DESIGN.md:555）。
- 投げなわと消しゴムは、最初は写真と札に効かない（手書きだけ）。投げなわの選び方（InkCanvasView.swift:2127-2137）も、台帳の取り消しの単位（Sources/TegakiCalendar/Ink/InkLedger.swift:124-128、線の add/remove だけ）も線しか知らない。写真も囲めるようにすると台帳を変えることになり危険が増すので、後の版にする。
- **↶**: 手書きの履歴は台帳の中（docs/DESIGN.md:561、InkLedger.swift:354-364）。1.5 で「最後の予定の変更を ↶ で 1 回戻す（最後の手書きの操作より新しいときだけ。↷ では戻さない）」が入る（docs/M7_PLAN.md:429）。写真と札もこの仕組みに乗せれば台帳を変えずに済む（本人向けの 2 には「直前の 1 回だけ」と書いた）。1.5 より前に作ると、この仕組みを写真のために先に作ることになる（3.7 の差 0.5 里程ほど）。
- 投げなわの「予定にする」は写真と札に出さない。

### 3.5 1.3 の横つなぎとの関係

- **同時にすると危険が掛け算になる**。1.3 はキャンバス・台帳・保存の道を作り直し（B_DESIGN §2.3）、取りこぼしと取り違いの守り（受け箱・安全網の merge・削除の守り・仮想の名前の守り）を線について作る（B_DESIGN §2.4 の 5・6・11、§7）。写真の項目もその全部を通すことになり、試す組み合わせが倍になる。1.3 はすでに約 4.4〜5 里程（docs/M7_PLAN.md:524）で、2/15 に出せなければ Duo の版を先にする決まりがある（docs/M7_PLAN.md:533）。さらに、指で動かす部品（1.5）がまだ無い。
- **横つなぎが先だと写真は楽になる**。写真を「中心のあるページに属する 1 つの項目」にすれば、線の持ち主の規則（B_DESIGN §4.1）がそのまま使える。紙の層は窓のページを原点をずらして並べて描く（B_DESIGN §2.3 の図）ので、紙の中身として描いた写真も一緒に並ぶ。B_DESIGN は、重点欄と書ける終日欄について「横つなぎの後なら最初から横につながる形で作れ、先に作ると作り直し（0.3〜0.5 里程）が要る」としている（B_DESIGN.md:633, :665）。写真にも同じ考えが当てはまる。案 B では週・日はこの形で作れるが、月はまだ横につながっていない。そのため月の写真は 1 ページの道で作り、新しい 1.7（月の横つなぎ）で横の道へ通し直す（+0.1 里程ほど【推定】）。これを避けたいなら「年の横つなぎの後（8 月ごろ）」にする。

### 3.6 プライバシー・App Privacy・規約

- **写真を選ぶ**: PHPickerViewController（SwiftUI の PhotosPicker も同じ仕組み）は別のプロセスで動き、利用者がアプリに許可を与える必要がない（Apple 文書）。Info.plist の写真の説明文も要らない（今の説明文は予定の 1 つだけ、project.yml:92）。カメラを入れると `NSCameraUsageDescription` と許可の画面が増えるので、最初は入れない。
- **撮影場所の情報**: 写真には撮影場所（GPS）などの情報が付いてくる。iOS 27 の SDK で、写真を選ぶ画面に場所を外す選択肢（`PHPickerMetadataOptions.removeLocation`。既定は外さない）が足されたので、既定では付いてくると見る。1.6 は Xcode 27 で作る（1.4 で移る。配布先は iOS 17 のまま、docs/M7_PLAN.md:480）ので、iOS 27 以上ではこれを使う。iOS 17〜26 でも外せるよう、貼るときに画素だけを書き直して付いた情報を外し（どちらの OS でも外す）、書き出しや PDF の共有で場所が漏れないようにする。
- **App Privacy**: Apple の定義では「収集」は、開発者や提携先が読める形で端末の外へ送ること（Apple App Privacy Details）。写真は iCloud へ送るので「端末の中だけの処理」には当たらない。根拠は、送り先が本人の iCloud プライベート DB で、開発者も他社も読めないこと（手書きと同じ。docs/PRIVACY.md:3, :24, :30-31、1.0 の回答の根拠 docs/DESIGN.md:942）。同じページの「写真などをアップロードする機能があれば種類を申告する」は、開発者の側に届く場合の話。だから「データの収集なし」のまま（docs/M7_PLAN.md:546）。`PrivacyInfo.xcprivacy` の集めるデータの型も空のまま（Sources/TegakiCalendar/PrivacyInfo.xcprivacy:9-10）。審査メモには日本語と英語で「写真は利用者本人の iCloud プライベートデータベースにだけ保存し、開発者は読めない」と書く。審査でこの扱いが通るかは、手書きで 1.0〜1.2 が通った根拠と同じなので通る見込み【推定・未確認】。
- **掃除と Required Reason API**: 掃除では端末のファイルの日時を読まず、消した時刻を自前の表に書く（既定）。ファイルの日時や大きさを読む作りにするときは、`PrivacyInfo.xcprivacy` に `NSPrivacyAccessedAPICategoryFileTimestamp`（理由 C617.1: アプリの中のファイル）を足す（今は UserDefaults と起動からの時間の 2 つだけ、PrivacyInfo.xcprivacy:11-28）。
- **文の追記**（約束を変える改定ではなく、対象を足す）: プライバシーポリシーの保存場所の表（docs/PRIVACY.md:22-28）に「写真（選んだもの）・文字の札」、§4（:46-51）に写真の選び方と撮影場所の情報を外すこと、§9（:75）の削除に写真を含めること。規約 第 3 条の機能（docs/TERMS.md:26-29）と第 8 条 2 項の書き出し（:80）。英語版（docs/PRIVACY.en.md・docs/TERMS.en.md）と公開ページも同じにする（既存の Pages の更新なので約束の範囲内、docs/M7_PLAN.md:567）。広告・他社の部品・開発者のサーバーは無いまま（docs/PRIVACY.md:17）。
- 「他人との共有をしない」（docs/DESIGN.md:89）も変わらない。写真も本人の iCloud の中だけ。
